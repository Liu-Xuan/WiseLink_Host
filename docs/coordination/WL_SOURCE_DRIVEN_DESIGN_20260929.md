## 1. 产品目标与本期完成范围

### 1.1 默认体验

工程师通常无需操作：指定工程文档目录出现新文件后，系统自动发现、取得原件、识别身份、比较版本、复用已有成果或进行必要初评／更新，并在资料库和事项Wiki呈现简洁认识。

工程师偶尔手工上传时，上传即触发文档读取和库内比对，不要求先填family、厂家版次、Matter或WorkItem。文件不因用户没有填写技术标识而无限等待。

手工上传的最低默认承诺是自动解析、归档和文件阅读；不得仅因上传了PDF就对任意材料创建目标评估。属于已授权工程处理范围、已有事项的有效新版本／补充，或用户明确发起工程评估时，再按统一策略继续。非工程资料保留为参考，不制造无关事项。

### 1.2 本期闭环

1. 工程文档云盘只读发现 → 原件受理 → family／版本核对 → 文件阅读 → 正常初评或增量更新 → 本人读取。
2. 手工上传与云盘导入共享原件、身份比对和阅读处理；重复输入不重复运行，也不扩大可见权限。
3. 已知787／737MAX错误通过合法后继修正，传到对应Overall和当前阅读面。
4. 解读和已启用中文阅读真实调度并交付，不把没有任务显示成处理中。
5. 一个有限多来源／目标事实场景真正读取并使用材料；有冲突也能自动完成有边界的分析。

### 1.3 非目标

不建设第二知识真源、memory-wiki、llm-task、Graphiti、通用事件总线、全量原子主张图或固定第二模型复审流水线。不接通所有厂家渠道、全部机队系统和完整实施时间轴。不执行正式采用、审批或放行。不把所有日报全量解析并逐期评估。支持的首批工程源以PDF为主；原生云文档等其他类型准确标记可用性，不默默使用未获准转换路径。

Host决定可信来源、对象、权限、版本、任务、提交和当前指针。扫描器只发现与读取；worker只解析获准内容；OpenClaw调查并提出候选；前端只读Host结果。数据库事务不跨云盘下载、MinerU或模型调用。

## 4. 来源策略：一次设置，持续自动执行

### 4.1 首批来源

| sourceKey | 范围 | 默认模式 |
|---|---|---|
| `technical-library` | `Q6uSfDwcDlBrUldWvZccoje8nXf`，TFU／ISI／FTD／FTAR及获准子目录 | 自动发现、解析、文档解读、按现行中文设置翻译；确认属于工程范围后自动初评／后继更新 |
| `operations` | `Oy1vfy8nslGZeUdBBkoczv0Fnxh`，每日航线运行信息 | Aily原生检索源，不默认进入完整评估队列 |
| 手工上传 | 已登录用户本次实际提交的文件 | 自动文档处理；工程后继是否触发由既定范围与真实归属决定 |

其他已登记来源本期不扩大启用。来源名称不授予权限；应用协作者可读也不等于所有用户可读。

### 4.2 最小策略信息（建议逻辑模型）

`sourceKey / tenantId / rootToken / policyRevision / enabled / processingMode / allowedFileKinds / delegatedExecutionIdentity / visibilityPolicyRef / translationSetting / bootstrapMode`。

策略版本记录“这次为何被自动受理”，不是模型置信度。先使用现有配置和来源记录；无必要不增加独立政策平台。若新增持久字段，记录其唯一消费者和为什么现有字段不能表达。

一次有效来源委托覆盖允许的必要子操作，不要求每份文档、每个阶段重新确认。入口受理自动形成确切文档范围的内部运行依据；这份依据用于追溯和验证，不是人工审批单。

### 4.3 原目录只读

允许列表、元数据、获准原件读取；必要的令牌获取仍按现有服务认证执行。禁止上传、覆盖、编辑、移动、改名、删除、评论、修改协作者及处理标记。禁止把结果回写到源目录。

限制按照API语义和工具能力执行，不简单禁止所有POST。初版只提供实际需要的读取操作；模型不拿云盘密钥、不直接调用通用云盘写接口。源文档中的指令属于资料内容，不能改变Host权限或工具策略。

## 5. 简化授权的实现

### 5.1 两条可信入口，共同派生运行范围

来源入口：有效来源委托＋获准根目录真实成员关系＋当前应用读取能力。

上传入口：已验证用户会话＋本次原件内容＋明确的默认处理策略／用户选择。

两者都转成Host生成的受理记录，再派发确切任务。浏览器声明`sourceKey`或`sourceChannel`不构成云盘委托。云盘服务不得伪造浏览器opaque session，不把服务导入写成某位工程师亲自上传。

现有代码若需要actor，必须使用已登记、合法的代理执行关系，并分别记录“授权责任方”和“实际执行服务”。不能随便选上传者或管理员来通过RLS。按来源自动执行不依赖工程师浏览器会话持续在线。

### 5.2 三道边界，各检查一次正确事实

- 入口边界：本次来源和用途是否合法。
- 执行边界：这个请求仍对应有效委托、确切内容及允许动作，租约有效。
- 内容读取／提交边界：来源仍可读、引用及输入版本正确、保存CAS未冲突。

统一实现规则，减少散落的字符串比较和同一次事实的重复装配；不把租约、来源撤权、版本CAS当成重复授权删掉。初次领取先验证领取能力，领取成功后才产生租约，不倒置依赖。

### 5.3 操作级能力

允许的文档处理能力：发现、取得、身份读取、登记／复用、解析、解读、已启用翻译、索引，以及策略允许的候选分析和更新。

自动处理不一并授予修改原件、变更来源策略、撤回其他用户请求、跨租户读取、任意恢复旧任务或正式采用。控制面可能需要合法的失败回执与租约释放，不应因为内容不可读而永远无法结束任务；控制与内容授权分别核对。

### 5.4 处理权限与用户可见性

去重仅在当前已授权范围中给用户可见反馈，不通过“库中存在”泄露其他租户或用户资料。相同字节可以复用底层存储，但不自动继承另一路径的可见性；来源关系分别保留。

一份派生工作同时使用多份私有材料时，默认保留现有完整来源读取规则，不因主文件公开就公开该工作。来源撤权后，新读取和新任务不能凭旧缓存继续使用；已加载会话在权限收缩后应按获准内容重建。

来源从目录移出与ACL撤销分开：已确认超出处理委托就停止该路径的新自动任务；已有成果能否继续读按真实权限与保留策略判断。扫描失败不等于撤销。

## 6. 扫描、候选与受理：不漏文件、不重复创建

### 6.1 正向变化不等待全目录完成

沿用`scanCandidates`的`pendingCandidates`。每次扫描在既有分页／条目／时间预算内运行；已经取得的新候选可以立即进入后续受理，完整性状态单独保留。[R5]

每次扫描只产生来源观察，不立即产生工程结论。提供方版本号、mtime、文件名和路径均只是变化信号，不能当厂家版次。

没有可靠版本号或mtime时，使用有界的周期内容核对或既有下载回执，不因统一`unversioned`身份永远漏更新，也不每分钟下载全部历史原件。具体周期根据文件量、平台限流和实际成本在实施中固定并记录；本文不声称当前已有特定时效承诺。

### 6.2 durable observation先于推进游标

扫描结果、未处理候选和继续位置沿现有checkpoint可靠保存。候选确认已受理，只能发生在原件/取得记录和可恢复后继请求都持久成立之后。不能先写“已处理”再创建任务。

崩溃重扫允许再次观察同一候选，由幂等约束返回原受理，不新建一份任务。部分目录失败不清空原候选，不把本次未出现的文件当成已删除。

### 6.3 稳定读取

先读取元数据，下载并计算实际哈希与长度，再核对可得的版本／修改标记。提供方版本在下载期间变化则丢弃本次候选提交并有界重试；如果提供方没有稳定版本标记，只能准确声明取得的字节快照，不能声称获得了不存在的快照一致性保证。

跳转下载地址按真实允许的来源域和安全路径处理；不根据文档内任意URL下载，不在日志泄露凭据。

### 6.4 历史首次导入

首次扫描建立完整清单并分批追平，不把所有历史版本同时推进完整初评。对同family已可靠识别的历史版本先登记，优先处理库内最新已知有效候选；已有旧评估仅在相关新变化下接续。

新到文件与已有用户任务优先于大批历史补处理，但历史任务有轮转机会，不能永久饥饿。扫描完整性未知时，页面说明“当前已取得资料范围”，不声称全库或发布方最新。

## 7. 解决“先解析才能识别，解析却需要DocumentVersion”的循环

这是必须显式实现的技术接点。不能仅在流程图上把“初步解析”移到“版本登记”前面，就认定现有接口支持。

### 7.1 优先复用现有预检

`documentIngressPreflight.js`已有实际字节身份、文号来源说明和前几页／受控元数据的身份依据；Catalog已有acquisition和preflight先于正式版本的结构。[R6][R7]

默认路径：取得原件 → acquisition/sourceArtifact → 精确重复查询 → 利用现有PDF.js／入口原文读取识别标题、文号与正式修订 → 预检和版本登记 → 完整MinerU解析。

“初步读取”不是额外全篇LLM分析，也不强制重复跑两个完整解析器。正文身份页不足时再按需扩大范围。

### 7.2 文字层不足时的受控候选读取

需要MinerU才能恢复身份时，复用现有出站worker和候选存储，增加最薄的acquisition范围识别模式（拟新增），任务绑定acquisition、sourceArtifact、字节及解析设置，而不是先伪造一个canonical版本。

候选属于原件快照；身份确认后，通过显式发布步骤形成与确切DocumentVersion绑定的新manifest。原候选和已有manifest不原地改绑。重用已生成解析时仍核对字节、设置、生产者和支持的格式，不重新执行模型。

### 7.3 无法确定身份时仍完成阅读

保持“未归族的取得记录／暂定来源阅读”，提供原文、可恢复内容和有边界的文件说明；禁止猜造厂家文号或版次来满足schema。若当前Reader只能读取DocumentVersion，则开发这一最小acquisition阅读投影，或使用明确非canonical的暂定类型；必须写明新类型及迁移，不伪称已支持。

身份不明限制自动合并和提升当前版本，不阻断其他文件处理，也不把填写family变成用户强制任务。之后身份确定用显式关联续接；旧临时来源引用仍可追溯，不静默重写历史。

## 8. family、版本、取得路径与事项的分离

### 8.1 四个不同身份

- SourceArtifact：实际原件字节。
- Acquisition：某次从云盘／用户取得的出处、时间和授权范围。
- DocumentVersion：某一具体publication family的正式版本或明确分类的来源版本。
- Matter／Work：围绕工程问题和目标形成的认识及其修订。

一个原件可以被多次取得；同一正式版次可有不同原件表现；同一文件可服务不同目标；同一事项可使用多份文件。不能用云盘路径替代family，也不能用最新WorkItem代替文档自身解读。

### 8.2 family键与版次判定

family主要由租户、发布者、文种／系列、规范化正式文号及必要适用域识别。保留原始文号与规范化映射。不能把所有FTD或所有787资料归为一个family，也不能把普通参考文件的文号误认成主文件文号。

厂家版次比较使用与发布者和文种相适应的规则；数字、字母、日期版次不混用字典序。明确修订标签、修订说明、正文和有效时间相互核对。系统解析修订、工作修订、云盘mtime、下载日期和文末生成日期均不能替代正式版次。

同标题、同ATA或文本相似仅用于候选召回，不足以自动合并。正式身份不清时保持独立，分析可继续。

### 8.3 决策表（建议结果语义，复用既有枚举或明确适配）

| 情形 | 文档处理 | 评估处理 |
|---|---|---|
| 字节及长度相同，范围内已有有效原件 | 新取得关联已有版本，复用符合条件的成果 | 不重复初评；目标事实实质变化则是独立后继原因 |
| 同family同版次，字节不同，仅非语义差异已获充分证明 | 保留原件变体和出处；符合Catalog合同才关联同版 | 不因换封面或下载戳重评；不能凭文本近似忽略图示差异 |
| 同family同版次存在实质内容差异 | 保留并标明变体／争议，不覆盖、不擅自造更高版次 | 比较相关范围，按条件分支完成认识 |
| 同family确认较新正式版本 | 增加不可变版本及当前选择记录，保存比较依据 | 延续原Matter，产生换版后继；不重复建事项 |
| 较旧正式版本晚到 | 补历史，不回退current | 必要时作为历史证据，不无条件重跑 |
| 新正式publication | 建family，先形成文件认识 | 来源策略允许时自动初评；无明确同问题关系默认独立Matter |
| 普通参考材料 | 独立来源登记／阅读 | 按实际用途关联，不自动成为成员或新Matter |
| 身份暂不能确定 | 保留未归族阅读，候选关系可见 | 可做文件分析，不提升为确定的目标结论 |

### 8.4 并发归族

用户上传与扫描可能同时遇到同一原件。先做有权范围查询，再用现有唯一约束和短事务处理竞争；冲突后读取已有赢家并核对范围，不再新建。

family当前指针使用既有generation／expectedCurrentVersion CAS。并行收到R2、R3时，输掉CAS的一方重新比较已有记录；保存合法历史版本可以继续，但不能让较旧版本覆盖较新版本。

不在数据库事务中等待下载或模型。相同哈希不自动复用另一目标的分析，也不提升另一个租户的可见性。

### 8.5 库内当前与正式有效性

记录库内当前选择与发布方有效性分别取得的依据。新版本如果明确未来生效或仅适用于某范围，可以先完成前瞻分析，但不能即时替换所有场景的当前依据。

不能从“本库未发现新版”推出“发布方没有新版”。不因身份冲突停住全流程，也不能以“必须自动完成”为由虚构currentness。

## 9. 最小数据设计与幂等边界

优先复用`dm_acquisition`、`dm_source_artifact`、`dm_ingress_preflight`、`dm_publication_family`、`dm_document_version`、`dm_currentness_decision`、文档run、ActionAttempt、WorkItem和Matter工作。新增逻辑职责不等于新增表。

允许最小增量：来源策略及其版本引用、可信受理的来源／用途信息、候选到取得的确认关联、确需的未归族阅读绑定、后继原因和待完成交付映射。每个新增持久字段都必须对应读取／恢复用途；禁止复制一整套grant、task、job、receipt真源。

### 9.1 建议的受理接口形状

```ts
// 建议业务契约，不是当前接口的原样声明。
type IngressOrigin =
  | { kind: 'DRIVE'; sourceKey: string; observationRef: string; policyRevision: string }
  | { kind: 'UPLOAD'; uploadRequestRef: string };

// origin中的可信内容必须从服务器上下文／记录恢复，不能信任浏览器同名字段。
type AcceptedIngress = {
  acquisitionId: string;
  sourceArtifactId: string;
  decision: string;                 // 映射现有preflight结果
  documentVersionId: string | null;
  familyId: string | null;
  requestRefs: string[];             // 已持久受理，不表示已执行成功
  reusedRefs: string[];
  pendingReason: string | null;
};
```

普通GET不创建任务。接收接口先完成持久受理再返回202／现有异步回执；响应丢失用同一请求读取恢复。

### 9.2 幂等不是只按文档ID

| 层次 | 幂等依据 | 不应做的事 |
|---|---|---|
| 来源观察 | 来源＋对象＋真实变化标记／本次快照关系 | `unversioned`导致永远漏更新 |
| 取得 | 来源对象与实际字节快照，或稳定上传请求 | 每次重试换UUID重复受理 |
| 版本登记 | 租户family、明确正式版次及实际内容关系 | 相同版次不同内容强行覆盖 |
| 解析／阅读／翻译 | 确切原文、解析与语义设置、语言及方法用途 | 一改无关配置就全部重跑 |
| 工程更新 | 事项／目标范围、确切输入和有意义变化请求 | 同文件不同目标共享私有结论 |
| 保存／ACK | 已有requestId、attempt、payload绑定和保存回执 | ACK超时再跑一次模型 |

来源策略修订必须在授权记录中可追溯，但只有影响实际处理输入／用途的变化才创建新业务任务。租约代次用于拒绝旧执行者，不应独自成为同一业务操作的新幂等身份。参数改变不能复用同一已提交请求意图。[E3]

## 10. 交付计划与自动调度

### 10.1 交付不是一个成功布尔值

以受理时的用途快照表达本次承诺：原文、文件解读、启用的中文、以及策略允许的评估。具体run可等原文就绪后再建立。

当前阅读服务要求明确parseRun和semanticRevision，因此不要在尚无原文时建立假reading run。先保存交付意图，前置满足后使用已有BEGIN。0067已有意图和授权链可以复用，但云盘入口需要真实来源委托，不伪装上传。[R1][R2][R8]

页面区分：未请求、未受理、已受理等待原文、排队、处理中、部分可读、完成、受阻。没有run但有有效受理记录可以显示等待依赖；没有任何持久依据不能显示排队。

### 10.2 复用现有消费者

来源监控属于确定性Host来源工作；C136继续是17c唯一动态消费者，本地worker继续解析。不要为每个来源新增一个OpenClaw cron。扫描是否可在原触发器内驱动受理，按实际部署能力接线，不假设现有C136会自动扫描云盘。

每次取得可执行任务，在时限／预算内可推进多个已满足依赖的步骤；每次提交仍重新核对租约和当前状态。不因“每分钟轮询”强制每个阶段再等一分钟。

解析等待不占用模型执行槽，单个坏文件不挡住后续文档。沿用已修的游标轮转与队首跳过；增加`nextEligibleAt`等字段必须有实际用途，不能为未知风险新建调度框架。

### 10.3 背压与恢复

初期沿用实测稳定并发，不凭来源变多扩大并发。大库补处理与新任务采用有界公平调度，慢源退避不影响其他源。SKIP LOCKED仅在既有队列领取适用，不用于生成完整文档目录或宣称全量一致读取。[E2]

技术失败保留受理和成果，按错误类型有界恢复。来源拒绝／撤权停止该范围内容操作；服务故障上报运维，不推给工程师逐项点重试。

## 11. 工程分析与认识更新

### 11.1 来源分层，不使用单一置信度分数裁决

经身份、版本和范围核对的正式文档作为该范围主依据。明确工程师复核作为高置信度输入，保留提供者、对象、时间和原话的不确定性。其他材料默认补充；经工具取得的正式文件仍为正式来源，不因通道降级。旧JobAid／Overall是派生认识，不是新增独立证据。

分别保存来源地位、内容性质、目标范围、时间与争议。模型不能自行把某来源升级为正式，也不能靠重复引用提高可信度。

### 11.2 追加变化，重建受影响问题

沿用ReviewTurn／ActionAttempt／工作修订表达补充、限定、反证、替代和无实质影响，不新增全量ClaimLedger。

模型输入包括当前问题工作、必要根来源、本次新信息及边界。模型提交变化理由及获准问题的新完整认识；Host保留旧历史和未改问题、计算实际变化并控制当前指针。

局部编辑仍服务于明确文本修复，但持续评估不依赖“找到旧文章第几段”。同一问题内的正文、风险、措施、分类和未决项需一致；标题与短述不得把候选原因写成已证实原因。

### 11.3 稳定输出

复用现有OpenClaw driver、工具Schema、Zod与Host物化。统一模型可写字段和实际保存合同；固定版本、身份、冻结字段由Host处理。引用从本轮实际读取结果选择，不猜ID，不近似替换错误引用。合法旧引用继承与本轮重新验证分别记录。

不同失败由不同机制处理：协议形状错误反馈字段；传输失败按网关合同；语义错误补证／改判断；保存不明读回。有限纠错不能在每一层相乘，也不能靠无限追加同一提示循环。

不使用memory-wiki／llm-task；当前已有同类知识维护和结构化生成职责，新增插件不会自动解决业务绑定。

### 11.4 冲突必须自动形成交付

先区分不同目标、时间、规范与现状。真正冲突时按既定规则有界取证；不能消除则给出共同成立判断、条件分支、优先依据及限制。使用现有`COMPLETE_WITH_OPEN_QUESTIONS`，继续Overall、保存和ACK。

不得统一设最高风险，也不得把所有结论抹成“请人工判断”。人工入口保留为可选补充，无逐段确认、无必须填完构型才能阅读的门槛。

权限拒绝、租约失效、损坏及未生成有效结果不伪装成业务未知或成功。无法安全合并family时完成独立文件阅读；无法安全采用某事实时完成有条件分析，而非虚构唯一答案。

### 11.5 更新传播

复用`overallRequested`／现有待综合恢复，问题保存后待更新义务持久存在。Overall精确绑定实际问题workRef；运行期间新信息到来则排为后继，不悄悄替换输入。

资料库、Wiki、索引和图谱读取同一份工作；确定性投影失败可重建，不再调用模型写另一份结论。当前阅读不继续无提示传播已撤回断言；历史引用仍指旧工作并带更正说明。

新版本不仅沿已知引用检查影响，也允许在同事项内检索新证据可能影响的问题。避免“旧判断未引用新来源，所以新来源永远无影响”的闭环漏洞。

## 12. 前端与可见性

保留已发布的三类入口，不改回工作修订列表作为Wiki目录。

- 工程文档：按family和明确版本组织，原文、解读、中文、范围和关联评估各自标识。
- 工程事项：当前问题认识、匹配Overall、关键条件／争议及新变化。
- 工作与历史：取得、解析、生成、更正和确切来源追溯。

上传默认不要求人工识别family；处理后显示“已关联已有版本／新版本／待归族阅读”等准确结果，提供可选纠正入口。同一文件有多个目标评估，明确对象范围，不把最后生成的一个评估当独立文件解读。

来源状态放在来源管理或运维区：最近成功扫描、完整性、待受理数、阻断范围和下一恢复条件。业务首页不堆技术错误，不每个正常入库都发送通知；重要变化可按现有通知策略合并呈现。

## 13. 0067／0068与新来源策略的迁移设计

### 13.1 已有事实必须尊重

R1说明：dev已执行过C198 0067，C199 0068待修；online未迁移。R1还记录平台拒绝GRANT／REVOKE，并存在对策略角色目标的改写；当前代码使用精确workspace角色、RLS及TRUNCATE触发器。[R1][R2][R3]

不要重新执行同名CREATE TABLE，不删表，不把原有迁移改写当成dev已经修好。先读回实际schema、策略target、角色继承、BYPASSRLS及触发器，再决定应用哪个未应用后继迁移。

### 13.2 不把来源驱动硬塞成browser upload

0067触发器明确处理`document_library_upload`和其持久选择。云盘acquisition不能改成这个sourceChannel来碰巧触发授权。[R2]

建议把可信校验和交付登记提炼为共同的Host受理步骤，浏览器与来源分别提供受控证据，再进入同一事务。SQL触发器若继续承担完整性，应验证对应可信来源，不接受任意READY preflight自证授权。

业务可统一，历史字段和来源类别不伪造。旧已迁移浏览器路径继续按原请求处理；来源级持久委托和自动派生选择通过最小新增字段／后继迁移接入。

### 13.3 服务SELECT边界的确定决策

`USING(true)`不表达actor或tenant过滤。R1明确当前精确服务角色能读表内所有行，Host selector才按tenant选候选；隔离测试还覆盖同表两个tenant，因此不能推定物理单租户。[R1]

发现任务允许在获准租户内跨actor读取最小元数据；选中后恢复确切actor。目标边界是可信租户范围，而非提前要求未知actor。若现有平台无法对服务会话可靠注入租户，应准确保留“服务受信＋Host筛选”的已批准边界，不伪称已有RLS隔离；进一步收紧使用可验证的服务—租户绑定或现有平台机制，不能信任浏览器自行设置的GUC。

新增普通窄策略不会收紧仍存在的宽松true策略；restrictive策略会与允许策略叠加，错误false可整体阻断。RLS不覆盖TRUNCATE，平台默认权限和语句触发器也需要读回。[E1]

### 13.4 发布与回退

按环境分别记录：迁移账本与实际对象、Host提交、17c Skill清单／校验、来源策略版本、启用状态。

推荐“兼容扩展→兼容代码接管→真实读回→收紧旧路径”。对已经迁移dev，先恢复其正确可访问状态；对未迁移online，先完成允许组合和回退演练。若旧权限必须立即关闭且无法兼容，按已获准的短时受理维护窗口处理，不宣称数据库和两个应用能一次原子发布。

源码集成基线使用实际已发布Host及C195或其后经确认修复，不把C186树整体覆盖过去。先暂停新增受理／领取、保留已持久任务及完成回执；必要时等待或安全释放在途租约。回退版本必须理解已经应用的最终结构，不能关一个开关后回到会被新RLS拒绝的旧写入。

开发阶段的新策略不追认旧`NONE`选择，也不自动回填全部历史授权。用户确需补处理使用明确的正常请求。文档分支保存本设计不代表运行代码、SQL或调度已改变。

## 14. 性能与可恢复性

重点测量首次实质可读和完整交付，而不是只看SQL数量或ACK。

| 类别 | 必记指标 |
|---|---|
| 发现 | 观察到新文件的时间、完整性、扫描页数、失败子目录 |
| 受理 | 观察→取得→持久受理耗时、重复命中、未受理原因 |
| 版本 | identity来源、精确复用／新family／新版／变体计数、CAS冲突 |
| 解析 | 下载字节、MinerU执行、候选续传、原件／设置重复复用 |
| 生成 | 首次解读、翻译覆盖、JobAid／Overall耗时、模型调用及无进展纠错 |
| 更新 | 新证据→问题保存→综合完成→投影一致的实际覆盖 |
| 运行 | queue等待、执行时间、worker运输故障、租约恢复、人工介入 |

输入规模、实例冷热、任务集合和模型版本一起记录。少量样本只报告方向、范围和具体覆盖，不宣称p95、可用率或固定秒级承诺。

日志保留字段路径、错误类、请求／版本关联，不打印原文、完整候选、凭据或私人意见。用户已有内容错误需要业务更正，平台故障需要执行恢复，二者分别统计。

## 15. 安全与自动完成的不变量

1. 原共享文件夹零写入。
2. 同一任务不同重试不产生重复业务副作用。
3. 同一原件多来源不合并权限，也不重复计证据。
4. 较旧版本晚到不回退current，重新解析不冒充正式换版。
5. 原始文档、历史解析和历史工作不原地改写。
6. 可选资料缺失／业务冲突不转为强制人工等待；安全和执行失败不伪报成功。
7. 模型只能提出候选，不能授予来源权限、选择服务身份或正式采用。
8. 所有当前阅读说明实际版本和覆盖；历史链接仍能回到当时依据。
9. Goal状态与生产调度分开；文档入库成功不等于工程结论可靠。
