# 1. 产品目标与价值

## 1.1 从一份文件看清一件事

WiseLink 面向航空工程文件与工程事项的辅助评估。它先保留文件自身准确的内容、结构、版本和来源，再将对当前工程问题有解释价值的材料与既有工作组织起来，按 JobAid 等方法形成连贯、可核对、可继续修订的工程认识。

工程师打开文件或事项后，应先看清：这是什么问题、文件提出了什么、对所选对象目前能判断到什么程度、有哪些决定性条件，以及下一项真正值得关注的变化。详细过程、材料贡献和原文按需展开，而不是将后台整理过的资料再次交给工程师自行归纳。

系统的价值不只是翻译或摘录。它应减少寻找依据、比较条件、复读历史及追踪改版的劳动，同时保留工程师的判断和正式业务责任。

## 1.2 四类产出，不相互冒充

| 产出 | 应回答的问题 | 不应冒充的内容 |
| --- | --- | --- |
| 文件解读 | 该版文件说明了什么问题、措施、条件和修订 | 目标机队已确认适用、已决定实施 |
| 对象评估 | 文件范围与本次目标的真实条件如何匹配 | 仅凭机型提及或标题产生的适用结论 |
| 事项当前认识 | 多份有效工程依据各自说明什么，参考信息如何帮助理解 | 被系统重新编写或批准的一份“融合工程文件” |
| 概览与知识阅读 | 哪些问题、变化和限制值得关注，如何回到依据 | 文档数、节点数、模型调用数或检查项完成数 |

默认阅读面应保留关键理由。决定判断是否成立的适用条件、否定、例外、期限与冲突不能为了简洁被隐藏。没有综合结果时，可以先展示已保存的文件解读或部分问题分析，但必须说明其范围。

## 1.3 设计优先级

优先保证原文与业务语义准确、现有信息能够产生价值、工作能够保存和接续、用户能够直接阅读与核对。翻译服务于工程师阅读；图谱、自动演示和视觉效果服务于理解，不作为后台初评的前置。

先完成真实可用流程，再按实际质量与成本优化。保留身份、权限、数据安全、来源、版本、事务、唯一约束、并发控制和正式业务确认。默认不新增通用 gate、额外 hash 体系、冻结平台、第二业务数据库或复杂调度框架。

# 2. 业务边界与当前范围

## 2.1 分清源文件、文件评估、事项认识和正式决定

| 对象 | 依据与内容 | 允许的更新 |
| --- | --- | --- |
| 受控工程文件 | 文件自身准确的正式版次、有效状态和原文 | 依正式发布、改版或受控更正登记；其他资料和AI不能改写原文 |
| 对该版文件的评估 | 该版完整内容、本版修订说明、相关方法和真实目标条件 | 因文件改版更新，或纠正对同一版原文的误读、遗漏与错误推导 |
| 工程事项认识 | 有关有效工程文件分别构成依据，参考信息辅助解释和比较 | 因有效依据、目标事实或有意义的补充信息变化而更新 |
| 我方正式决定及实施 | 对应程序、授权、审批和原始业务记录 | 通过现有正式入口处理，不由候选保存或普通讨论自动改动 |

**参考可以改变理解，不能跨文件改写受控要求。文件没有改版，不等于系统此前的错误理解不得更正。**

不得将“本版SB的条款未被正式修订”扩大为“该事项所有风险、执行条件及安排都不可能变化”；也不得依据FTD、会议纪要或检索摘要宣称“SB新增了某项规定”。来源的具体地位和用途由实际身份、内容及任务确定，不按 FTD、SB、SL 等名称一刀切。

## 2.2 初评与持续更新的目标流程

初评从正常受理、准确原文与语义阅读开始，建立本轮上下文，按问题调查、开展适用性和 JobAid 分析，分次保存有价值工作，再以确切结果形成综合。**后台工程分析使用原文和原始记录，不以中文译文作为事实输入，也不等待全文翻译。**

持续更新有两类入口：工程师明确请求；既定授权与已启用策略内的真实信息变化。文件自身改版、正式依据新增、有效事实更正以及已登记复看条件可以进入正常后继流程。普通聊天、索引刷新、图谱布局变化或任意相似命中不无条件触发重评。

自动策略尚未接通的来源保留明确的人工入口，不能展示为已自动处理；已有可读材料的分析不等待所有外部接口、全库扫描或构型数据齐备。

## 2.3 文件族与事项组织

文档 family 是同一具体文件的版本集合，不是“所有SB”或“所有FTD”的类别。按用户已确定的组织原则，没有明确归属的正式工程文件 family 默认形成独立事项；同family新版本延续原事项，不因改版重复建项。

解析发现与既有事项确实承接同一问题、调查或措施脉络时，依据实际内容归并或关联。普通引用、同ATA、同设备、标题相似、图上相邻不足以认定同事项。日报、会议清单等混合资料按实际问题或记录关联，不把每个附件和每一期日报无条件变成一项独立工程事项。

事项材料区分成员、参考和预期资料。原文明确提及尚未收到的后续文件时，可以登记预期身份、来源时点和作用；不制造其正文、正式有效状态或已覆盖结果。材料到达后核对身份与范围。

人工归入、保持独立、改为参考、合并或拆分保留修改依据，不被再次解析静默改回。综合文件可按章节参与多个事项，不复制原件；组织关系不扩大资料可见范围。

## 2.4 当前技术路线与非目标

保留妙搭 Host、PostgreSQL/Drizzle、FileService、现有 Reader、官方 Hosted OpenClaw、Aily、ActionAttempt 和正文优先的工作保存。默认解析路线为 Host 官方插件配合 PDF.js；Translation V2 独立提供中文；MinerU恢复不作为本批前置。

不新建第二知识真源、独立向量库、图数据库、通用事件总线或桌面常驻产品执行器。多维表格可作为后续有明确边界的计算端，但不因它可批量填充就迁移业务任务真源，也不成为当前更正闭环的前置。

# 3. 身份、版本与有效性

## 3.1 必须区分的身份

| 名称 | 职责 |
| --- | --- |
| Document / family | 同一具体文件的稳定业务身份与版本集合 |
| 厂家或发布方正式版次 | 由来源文件与受控登记确认的出版版本，不由解析次数生成 |
| DocumentVersion | Host绑定的确切来源版本；不能同时当作WorkItem或事项工作修订 |
| 元数据修订 | 标题、文号、机型、ATA等提取或登记的更正；不擅自改变正式版次 |
| parseRun / 解析修订 | 对确切源版本的一次解析生产及其产物 |
| semanticRevision | 绑定确切原文解析的章节、角色和范围映射修订 |
| SourceRef / 原生selector | 可回到准确原文范围、表格、图片或原始记录的位置 |
| WorkItem | 既有文档评估任务对象，不用它伪装所有工程事项 |
| EngineeringMatter / 事项 | 组织同一工程问题脉络、材料和持续工作的业务对象 |
| workRef / workRevision | 已保存工程工作的确切版本，可包含多个完整问题 |
| ActionAttempt / 请求 | 一次受理、领取、执行及结果关联，不等同运行会话 |
| DialogueThread / ReviewConversation | Host保存的业务讨论及其归属、可见范围 |
| OpenClaw或Aily运行会话 | 平台执行上下文；不能代替Host工作、权限或来源记录 |
| Host commit / release、Skill build | 技术代码、部署和安装身份，分别记录实际生效情况 |

解析修订6不等于厂家R06；当前工作15不等于文件第15版。前端、日志、模型输入和导出使用一致的含义。

## 3.2 “最新取得”不等于“最新有效”

每个family依据实际受控登记、来源核对和有效性信息确定本次采用版本。至少能够说明采用哪个版本、依据什么核对、何时核对、是否存在尚未取得或不可读的新版本。优先复用已有记录，不为此建立单独的版本认证平台。

本地上传时间、文件名中的日期、解析完成时间和工作保存时间均不能单独证明发布源现行性。`RESOLVED_EXACT`仅表示身份解析明确，不等于该文件现行有效。

未核实时显示“当前已取得版本／现行性待核”；已知最新版不可读时，显示尚未覆盖的范围，旧版仍可作为历史阅读，不冒充最新依据。不同family各自取有效版本，不以事项中最新日期的一份文件覆盖其他文件。

来源明确要求使用某一特定引用版次时，保留其精确引用和用途；可以另行核查是否存在更新，但不能静默替换。正式发布体系中的独立文件或更正通知按其自身身份、作用范围和受控关系登记，不靠语义相似生成替代关系。

## 3.3 历史与运行中的新变化

任务启动时绑定本次依据、工作版本、目标和有效授权。运行中新资料进入后继范围，不无提示地修改正在计算的输入。来源明确撤回、权限变化或本任务前提失效时，按实际生命周期处理，不能为了维持运行而继续将失效依据称为当前依据。

历史评估保持当时精确来源；新工作可以解释哪些旧认识被修正或仍然成立。无需重写历史workRef，也不把旧失败改标成功。历史工作被引用时，应同时读到其适用条件、当前是否已有更正以及必要的根来源。

## 3.4 不同“当前”状态分别表达

源文件是否有效、解析是否发布、工作是否为最新保存、Overall是否覆盖该工作、结果是否已正式采用，是不同维度。不得用一个 `CURRENT`、绿色勾选或“已完成”同时代表它们。

# 4. 系统职责与运行边界

## 4.1 组件分工

| 组成 | 负责 | 不负责或不得推定 |
| --- | --- | --- |
| Host | 身份与租户/对象授权、文档与版本、事项关系、上下文、任务、工作保存、事务/CAS、正式采用边界 | 不把模型输出、普通假设或搜索摘要自动变成受控事实 |
| PostgreSQL / Drizzle | 稳定业务记录、工作修订、任务及必要待处理记录、可重建检索投影 | 不用业务事务等待远端模型和大文件处理 |
| FileService | 原件、图片、解析包及较大产物的持久存储 | 临时签名链接不充当稳定业务身份 |
| 官方解析/文本插件与 PDF.js | 既定职责内的解析、文字层读取、语义辅助、翻译或定点生成 | 插件调用成功不等于结构、工程内容或来源现行性已通过验收 |
| Reader与语义映射 | 完整语义阅读、章节展开、准确原文定位、译文辅助 | 不改写源文件、不创造正式要求 |
| 官方 Hosted OpenClaw | 开放式调查、跨来源比较、连续上下文和动态问题组交付 | 不拥有业务授权、当前工作指针和正式业务决定 |
| Aily | 自由讨论、解释、焦点承接，按权限读取当前工作并协助归集贡献 | 不另存一套工程当前结论，不自动分享私人内容 |
| 原始业务系统 | 构型、故障、拆换、执行、可靠性及正式审批等原始事实 | WiseLink候选不替代其正式记录 |
| 页面、Wiki、检索和图谱 | 同一工作及来源的阅读、发现、导航和关系投影 | 不独立生成另一份综合意见，不通过布局推断适用性 |
| Base（后续可选） | 经实际接通的独立计算输入、结果及回执 | 不接管Host工程当前版本，不与另一个执行端竞争保存同一请求 |

# 5. JobAid、适用性与综合判断的方法

## 5.1 原文方法与系统工作组织

方法依据包括《局方及厂家源文件评估》JA-DS093和《基于风险的工程评估标准》JA-AC，以及实际适用且已取得的程序。本文承接所提供材料中的方法解释，不宣布其为本轮重新核实的全部现行程序。

JobAid的业务要求、分析方法、防遗漏提示、条件性检查、表单说明和实施管理要求分别发挥作用。原文不创设超出相关程序的新程序；发生冲突应依据现行有效程序处理。具体文件类型是否适用某种评估程序，按方法原文范围核对，不将一套方法自动推广到全部文件。

现有150项是旧实现拆分，不能作为问题数量、模型调用数或本轮完成标准。原始要求的可追溯关系保留；重复调查可以合并，错误推导可以说明依据后撤回，后续实施要求放回对应阶段。

## 5.2 围绕完整工程问题开展分析

一个完整问题通常需要讲清背景与现象、触发条件、后果、证据、措施针对性、限制和当前认识。内容按实际情形合并和深化，不生成另一张固定问卷。

JA-DS093 §5.3.1（所提供PDF第9页）将背景、措施、适航、安全、可靠性、维修运行、资源等因素放入连贯评估意见；参考、工时、估价等按需填写。系统据此保存完整工程正文，而非要求模型先将同一解释重复分配到所有字段。

适航性、安全性、可靠性、经济性、服务质量等影响分类可协助组织，但不能代替技术问题分析。厂家说明、原始记录、工程师陈述、系统推断和候选意见分别表达。不能以厂家推荐较低结束自身风险判断，也不能以一段参考推断冒充厂家正式要求。

## 5.3 适用性评估和管理继续作为核心能力

适用性至少分清四个问题：文件本版声明的范围；当前目标的实际事实；二者是否匹配；措施实施或验证还有哪些条件。SB Effectivity、机队实际构型、工具兼容性和我方安排优先级不能压成同一结论。

按机体、发动机、部件或LRU等实际情形使用相应判断方式。已有可靠结论确认不适用时，可以停止该目标下不必要的详细评估；其作为背景的价值和其他独立事项的分析不因此一律终止。改版涉及有效范围变化时重新核对。

缺少构型、安装或执行记录时，仍可解释原文范围、机理和措施前提；具体匹配保持待核。未查询不等于零记录，未找到不等于不适用，机型分类不等于效应性匹配。普通口头陈述可作为明确归因的分析前提，不能直接更新受控构型。

关联文件有自己的目标适用性，不能复制主文件结果。仅用于背景不自动意味着 `NOT_APPLICABILITY_BEARING`；只有材料本身不承载相关适用性主张时才使用该含义。

## 5.4 风险分析与措施比较

选择适合当前问题的定性、定量或组合方法。明确后果及其成立条件、发生可能性的依据、暴露、探测和控制能力；有足够定性依据时不强求不存在的精确故障率，依据不足时不编造风险分数。

实际采用JA-AC矩阵及提级要求时，保留所用方法版本、情景及分级理由，由Host既有确定性处理计算。不同风险分类体系、SAE事件类别、厂家推荐级别与我方风险等级不能因字段名称相似而互相替代。案例中的历史机队数量、故障和措施状态只用于理解方法，不成为当前飞机事实。

措施分析说明解决什么、未覆盖什么、适用前提、替代或补充路径及实施约束。识别重要风险后不能只留下分数；但形成措施候选不等于已经批准执行或落实资源。

## 5.5 防遗漏、表单和后续阶段

重要系统SB/SL等条件性检查须保留原文完整语境。检查单的防遗漏作用不等于所有可能条目都是全部初评的固定前置。原提供的JA-DS093 PDF未包含其正文提及的附件5，不能以旧150项映射宣称已核对原附件；该局部缺口不阻止按已取得正文形成有范围的候选。

需要编写工程文件、修订手册、落实器材、安排实施和收集完成记录的要求，在相应业务阶段处理。初评识别重要影响与后续义务，但“尚未实施”不等于初评失败。正式执行、不执行、延期、审批及放行仍由对应业务入口决定。

## 5.6 不确定性与阶段性完成

Gap Ledger承接决定性未知和证据需求，不是开发缺陷总表。每项未知说明限制哪一条判断，以及当前是否有值得执行的获准获取路径。一个缺失构型可共同影响多项分析，不重复生成多份相同提醒；无来源的虚假依赖经核对可以撤回。

保留既有有用的 `RESOLVE_NOW`、`DEFER_TO_REVIEW_DATE`、`OUT_OF_CURRENT_SCOPE` 等处置含义，但不要求每个问题都填满处置枚举、日期和监控字段。实际需要机器复看时才使用现有 `reviewConditions` 并接通消费者，不能只有正文写了“定期复看”就宣称已自动监控。

`PRELIMINARY`、`REVIEWABLE`、`CONFIRMABLE` 等已有成熟度，如被现行接口使用，应说明实际含义；不能用状态名代替依据，也不新增同义成熟度平台。可供复核不等于正式批准，信息尚不完整也可以完成本轮有价值的条件性分析。

# 6. 有限输出下的调查、更正与可靠运行

## 6.1 两种生成方式，共用同一工作

| 方式 | 适用情形 | 正常交付 |
| --- | --- | --- |
| OpenClaw开放式调查／接续 | 需要发现问题、读取新资料、比较多种解释 | 连续上下文中动态选择完整问题组，分次保存实质认识 |
| 官方插件定点更正 | 错误对象和必要语境已经明确，无需重新调查整个事项 | 完整修改实际受影响的问题内容，经同一Host保存服务产生新工作或核对记录 |

不要求每次初评都先由OpenClaw分析、再由第二模型重写报告。正常调查形成的完整成果可直接保存。更正需要额外调查时回到已有调查能力，不硬写答案。

任务受理时明确实际执行用途和获准路由；不在失败后静默切换模型、插件、数据接收方或权限范围。平台未暴露具体模型时记录可证实的配置，不编造下游身份。本文不认定所有入口具有相同16000上限，也不再把扩额作为近期可用性的前置。

## 6.2 连续上下文与多次保存

Host保存业务会话、贡献、工作和来源；OpenClaw保留运行上下文；每个请求/Turn/ActionAttempt标识一次真实操作。请求更新不必等于重新开始讨论，长期会话也不等于每轮灌入全部历史。

首次取得整体问题、主要原文结构、有关方法和既有工作。后续优先传新增资料、必要原文、当前继续方向及简短保存回执，避免反复发送大目录、全部字段说明和旧失败日志。关键条件、否定、已撤回前提与准确来源入口必须保留。

```text
理解与按需读取
    → 形成本次能够完整回答的一组问题
    → Host正常保存并返回确切workRef
    → 同一运行上下文继续下一组或深化已有问题
    → 最后核对共同前提、冲突、措施覆盖和未知
    → 保存必要综合并结束本轮
```

一组可以是一项或多项问题，不固定数量。问题可以跨章节取证，不按PDF碎片隔离理解。输出传输批次、翻译语义块、工程问题和完整工作修订是不同粒度。

首个保存点必须有实质理解或有依据的条件性判断，不能只有标题、计划或“准备保存”。A已保存、生成B失败时A继续可读，后继只处理未完成或实际受影响范围。最终综合不重新抄写全部问题和历史。

授权收缩后，旧会话记忆不会因工具检查而自动清除；按仍获授权资料重建或限制运行上下文。会话丢失时从Host保存工作和必要原文恢复，不将桌面临时文件视为唯一进度。

## 6.3 正文优先的工作内容

默认成果以“稳定问题身份＋问题表达＋完整工程正文＋准确引用”为主。正文承载前提、措施范围、风险解释、反证、未知及取舍；只有确需程序计算、筛选或触发的内容才使用相应稀疏结构。

原接口已存在的风险、措施、要求处理和未决问题字段按实际需要保留和消费，不要求每次再重复生成所有字段。不能把正文塞进虚假的旧statement后补空数组，也不能新建一个“小正文转旧大JSON”模型环节。

Host负责业务主键、版本、授权、来源映射和实际运行标识；模型仅使用当前获准的引用标识。引用短别名必须映射回确切来源，不由模型猜路径或自动近似修复错误ID。引用存在只能证明可定位，不能由程序自动证明其语义支持。

工作当前指针可以随正常候选保存推进；正式采用指针独立。正文、标题、限制和实际可见的退役均属于需要正确保存的内容，不能只检查仍存在的问题数组而丢弃合法撤回。

## 6.4 定点更正的输入、范围与完成

更正前核对四处：实际输入、原始生成结果、持久工作、页面/检索/Overall读模型。输入清楚列出目标工作与问题、完整目标内容、待核对的具体表述、必要根来源、实际参考用途和相关综合。

旧工作是待核查的派生认识，不是必须复述的证据。无关问题的全部历史、安装记录及旧轮次说明不进入更正输入。短文可以保留完整原文，不为追求小输入丢掉条件。

生成正确但保存遗漏时修物化；保存正确但页面读旧结果时修读取；生成仍错误时修本次任务范围与依据。只有实际错误所在字段需要增加更新能力，不把发现保留字段等同于必须重发整份报告。

更新某个问题时，使其修改后的完整内容可独立阅读；未提交字段按明确语义保留，显式删除/退役与未提交不同。question、body、requirementHandling、openQuestions、措施、风险和分类凡受同一更正影响均需一致处理。未受影响其他问题保留，不将“四个必须不变”固化为普遍规则。

Host依据前后实际内容判定变化范围，模型提供更正理由。未变化状态不得出现在“本次已修改”清单。核对后无实质变化，在现有请求/处置记录保存比较范围和理由，不强造workRevision；退役、真实文字语义变化和正式源版本覆盖变化不能被当作无变化丢弃。

已知疑点随对应问题、Wiki和知识读取呈现，不宣布整份工作无效。更正涉及当前综合时同批更新；尚未更新则准确标明Overall基于哪版工作、未覆盖什么变化，不等到后续跨事项项目才处理。

## 6.5 任务管理、唤醒与退避

Host决定任务归属、可执行范围、版本、期限、恢复和保存；既有Hosted原生job可继续承担云端唤醒，确定性消费者负责领取和机械调用。队列检查不需要LLM判断。

已经正常受理、获准且可执行的请求优先取得；没有此类请求时再检查自动评估需求。一个无关旧自动请求或绑定工作读取失败，不应阻止新请求领取。本任务自身必要来源、授权或版本冲突仍必须处理，不能借任务隔离绕过。

| 情况 | 正常处理 |
| --- | --- |
| 确实无任务 | 正常IDLE，不调用LLM，不增加业务失败 |
| 单个请求或旧绑定错误 | 准确归属并可靠记录，其他独立获准工作可继续 |
| 必要来源或鉴权明确拒绝 | 标明具体恢复条件，不无限原样重试 |
| 明确临时服务错误 | 在已有预算、授权和限流约束下有界恢复 |
| 整个Host不可达或统一身份失败 | 保留系统级失败和合理退避 |
| 原生length且无完整结果 | 不补半JSON、不按“空文本”原样叠加重试 |
| 一般502或结果不明 | 不猜测为length，先依据可取得的请求记录定位 |
| SAVE结果未知 | 查原请求和回执，不换身份或ID盲目重复提交 |
| 用户取消、租约失效或绝对期限已过 | 正常收尾，保留历史；有需要再受理合法后继 |

业务任务失败已经可靠处理，不必等价为整个消费job失效；无法持久处理或未知系统异常仍上报。不得统一catch后返回假成功。

排队等待、执行预算、服务冷却和绝对期限分别表达，复用已有时间字段和任务设施。不得静默延长已受理请求。必要时在原授权内通过受支持入口做一次操作员恢复，并另行证明自然调度；不以不断强制run替代产品自运行，不修改托管内核或周期性清零错误计数。

## 6.6 可观测性与容量度量

分别记录受理、排队、领取、上下文装配、读取、模型等待、完整结果、保存及回读。适配器调用次数、内部原生生成次数、纠正与恢复分别统计；可取得的token和费用按实际口径记录，缺失不猜测。

不把多个截断响应相加为一份完整报告，不把大输入HTTP200当可靠理解，不承诺未经实际材料证明的上下文阈值、成功率或固定分钟数。优先优化重复输入、重复读取、空等和无进展重试，而不是继续放大配置数字。

# 7. 原文语义、事项关系与材料选择

## 7.1 解析结构与业务章节

解析应保留真实正文、阅读顺序、标题层级、表格、图片、警告、编号、脚注和来源位置。语义映射在原文之上说明章节和贡献，不复制或修改受控原件。

已确认的文种与厂家profile可帮助识别栏目，但不能从被引用文件号猜当前文件的厂家或类型。未知类别保留通用作者目录；识别不准时保留原题、相邻上下文和限制，不补造原文没有的章节。

| 资料示例 | 可以帮助导航的语义范围 | 约束 |
| --- | --- | --- |
| FTD | 本版修订、适用范围、问题描述、背景、状态、临时措施、最终措施、用户措施、里程碑、影响或关联分类 | 仅为示例，按实际原件识别；Status或Final Action不得因插件标题等级错误混入另一个栏目 |
| SB | 改版说明、背景、Effectivity、符合性/推荐、工时、器材、施工步骤、附录、附图及限制 | 不假定所有厂家具有完全相同目录；同一名称可能出现在不同父范围 |
| 报告、纪要、运行信息 | 事件、分析、措施、行动项、日期及原始记录位置 | 汇总说明与原始事实分开，计划完成不等于实际实施 |

章节成员区分直接正文与子树。按章节读取应带必要祖先正文、表头、脚注、条件和原始覆盖限制；role只帮助查找，不能成为遗漏其他有关原文的硬过滤。空栏目、明确None、明确N/A和未读取不能混为同一状态。

纯标题层级或定位调整与工程内容变化分别判断；semanticRevision改变不自动全篇重译或重评。若此前结构错误使分析漏读条件，则更正相应阅读范围并续接受影响判断。

## 7.2 资料贡献与关系最小表达

原文件中保留的多个维度各有用途，但按实际问题稀疏使用，不要求为每张卡片填齐。

| 维度 | 说明什么 | 不能推出什么 |
| --- | --- | --- |
| DocumentType | 材料实体类别，如FTD、SB、SL、AMM、报告、记录 | 仅凭类型确定权威、适用或强制性 |
| ContributionRoles | 信号、调查更新、技术背景、临时/最终措施、施工说明、出版影响、反馈等贡献 | 贡献为最终措施就等于目标已执行或所有风险关闭 |
| RelationTypes | 引用、修订、替代、前置、同时措施、实施承载、出版影响等具体关系 | 普通引用自动变为REQUIRES_BEFORE或SUPERSEDES |
| EvidenceStance | 对明确判断的支持、限制、反驳或中性关系 | 一条来源链接自动证明某个主张成立 |
| TargetApplicability | 对特定目标是否适用、未评或未知 | 主文档适用结果可复制给其他材料 |
| Currentness / SourceAuthority | 在明确核对范围内的现行性和来源属性 | 库内最新版即发布源有效版；经RAG返回即变成非受控原始资料 |
| 召回优先级与关系可信说明 | 决定先读什么、关系解释还有何限制 | 排名靠前即有效依据或事项成员 |

原有 `REFERS_TO`、`REVISES`、`SUPERSEDES`、`REQUIRES_BEFORE`、`REQUIRES_CONCURRENT` 等字段保留明确语义。修订指向同一文件的受控版本链；正式替代或前置关系必须有实际内容、范围和来源，不能由主题关联制造。

## 7.3 显式引用与实际读取

ReferenceMention记录当前源文在何处提及对象，包含准确提及位置、原文写法和目标身份解析。提及处的SourceRef不是目标文件正文；声称使用目标内容时，必须有目标自身的读取范围。

同一目标被多处引用可聚合展示，但保留不同位置及用途。身份歧义、未入库、无权、不可用和未支持分别表达。标题缺失可以留空，不能生成貌似正式的文件名补齐。

原有RelatedContextSnapshot或EXPLICIT_PREVIEW仅说明相应历史预览，不把标签改为true来伪装实读。新任务以实际来源取得和使用记录说明消费；保留有价值历史，不为旧预览协议继续建立长期兼容层。

## 7.4 按问题挑选完整有用范围

优先主文件和明确关系中的实际相关内容，再根据问题获取补充资料。纯施工AMM步骤通常不自动装入机理背景；分析施工条件、工具、接近、停场或维修要求时，按需读取对应内容。不是按文种永久禁止。

每份入选材料能够说明帮助回答什么、选了哪一段、来源和版本是什么、有什么限制。完整目录保留在Host，不需要全部进入模型。发现、选入、实际读取、用于判断和正式采用分别记录，已读未用不能自动标为“经比较无影响”。

# 8. RAG、Wiki、检索与跨事项知识

## 8.1 三类内容使用同一来源链

| 内容 | 保存职责 | 再次使用 |
| --- | --- | --- |
| 来源阅读视图 | 完整语义范围、结构、图表、条件与来源映射 | Reader、翻译、原文检索及调查 |
| 工程工作内容 | 完整问题、前提、措施边界、风险解释、反证、未知与变化 | 本事项续接、Overall、跨事项参考 |
| 问题索引与知识页 | 问题和对象导航、精确工作引用、来源入口及必要状态 | 发现、阅读、跳转、图谱投影；不另维护一份可独立修改的综合正文 |

工程工作可以使用中文表达并供后继模型读取，但它属于派生认识，不是文件中文译文，也不是新的原始证据。后继分析核对条件和根来源，不因其由系统保存就提升来源地位。

## 8.2 互补检索渠道

显式引用、问题脉络、知识空间RAG、有限关系邻居、工程师附件和Host历史均可提供线索。不是固定六层调用流水线，也不要求每次全部查询。

RAG是发现渠道而非权威等级。保留实际返回片段、查询、来源、可见版本/取得时间和授权范围；能核实原始资料身份时不因检索方式抹去它。摘要命中不等于原件已读，Drive文件搜索也不等于知识空间RAG。

显式引用未解析时保留精确失败，不用模糊命中冒充该文件。需要更多背景时允许继续搜索，但结果与原引用分别表达。可选检索不可用则继续现有材料分析，决定性缺口明确限制相关判断。

## 8.3 搜索保存的完整认识

复用现有工程问题检索和PostgreSQL投影，按SOURCE、RECORD、WORK分别识别命中性质。仅存在写入类型或索引条数，不等于查询和模型消费已经接通。

默认工程工作搜索使用明确当前工作指针，历史查询显式选择并显示版本；原文搜索同时说明源版本及现行核对范围。问题正文、措施限制、风险理由、未知及有意义的脚注不应因ID字段限制或短摘要被截掉。

文号、件号、软件版本等按适当的精确检索处理；一般文本检索复用现有分词和参数化查询。返回前执行真实对象权限检查，不暴露未授权的正文、摘要、标题、计数或hasMore线索。Top-K仅是本次返回范围，不作全量统计。

索引失败可由保存的确切工作和原文重建，不重新调用模型。根来源和已知更正说明随完整工作返回；不得让旧绝对判断因检索摘要省略条件而重新成为“知识”。

## 8.4 三种跳转

| 链接 | 绑定 | 默认行为 |
| --- | --- | --- |
| 对象导航 | 稳定文档、事项或既有主题身份 | 打开该对象页面，显示实际采用的版本 |
| 原文依据 | 准确DocumentVersion、parseRun、SourceRef或原生selector | 直接定位原文，并允许展开上下文 |
| 既有工作引用 | 准确subject、workRef和issueKey/claimId | 读取当时完整分析、条件、来源及当前更正提示 |

Wiki正文可自然链接其他页面，图谱可辅助探索，但导航链接不自动成为实际证据使用，也不自动合并事项。准确来源已经明确且权限有效时，不要求先选择事项才允许读原文。

## 8.5 跨事项复用与避免循环强化

后继分析先检索相关问题，展开完整论点、适用条件和限制；必要时回查根来源，再与本事项有效工程文件和实际目标比较。可以复用解释方法和调查经验，不继承另一事项的构型、发生概率、风险分数、实施或批准状态。

同一根来源经翻译、摘要、旧工作和再次RAG召回，不能计为多份独立证据。保存实际引用的旧工作与根来源；知识页和搜索投影不是额外权威来源。

来源变化可沿实际使用关系反查问题。没有旧链接的新线索也可以被检索发现，不将依赖图当成唯一认知范围。首批以完整问题级关联为主，不先拆成全量原子主张图谱。

## 8.6 图谱与演示

图谱使用同一文档、版本、事项、问题和来源关系，支持文档、事项及后续技术域/全景探索。边可展开理由和来源；图的距离、相似度、节点大小和连通性不是适用性或风险证据。

未接入的数据、领域/全景示例和隔离样本明确标识。演示复用业务阅读组件但仅允许导航、过滤、展开和视角操作；不启动真实Agent、保存工程结论或采用结果。退出恢复原对象、版本、阅读位置和草稿，不能用样本替代真实读取失败。

# 9. 初评、改版、参考变化与交互复核

## 9.1 初始评估

正常受理确认文件身份、正式版本与来源，解析形成可读结构和准确定位。主文件初次阅读保留整体范围，识别真正需要研判的问题；按需取得有价值参考和当前目标事实。

适用性处理文件范围与目标匹配，JobAid组织技术认识和方法，Overall核对实际保存工作。各操作继续使用既有任务设施，按真实数据依赖衔接，不因原实现有四个ActionAttempt就强制串行翻译后分析，也不把多个共享版本写入无控制地并发提交。

正文足以完整表达一个问题组时及时保存。初始综合消费确切工作，不凭保存次数或读取数量判断完成。必要来源无法取得时只限制相应判断，已有依据支持的有价值工作继续。

## 9.2 文件自身改版

```text
同family正式新版本到达
    → 确认身份、正式版次与有效性
    → 读取本版自身修订说明
    → 读取新版实际相关正文与完整条件
    → 核对以前评估及关联工程文件的影响
    → 保留仍成立认识，修改受影响内容
    → 保存新版覆盖及必要综合
```

修订说明是首要定位入口，不替代正文，也不替代以前评估的覆盖核对。JA-DS093 §5.3.1第9项（所提供PDF第9页）要求改版评估覆盖以前各版本评估意见并关联此前工程文件；实现上可先核对历史清单，再按影响展开，不必每次把所有历史重新生成。

典型SB的Revision Transmittal Sheet等自带说明用于理解改版原因和内容；实际文件缺少说明或无法读取时据实标记，不由模型补写。系统diff与发布方说明分别展示，差异需要核对而非自动断定谁错误。

新版带来新的正式依据，即使结论文字不变，也须有本轮实际比较范围、结果和新版本覆盖记录。不得仅因正文相同沿用旧覆盖，也不必为没有语义变化重新生成整份正文。是否产生新工作版本按既有依据绑定/覆盖协议决定，不能把新来源偷换进旧历史记录。

## 9.3 不同变化，不同处理

| 变化 | 进入什么处理 | 不应发生 |
| --- | --- | --- |
| 同family正式改版 | 该文件评估及相关事项的影响分析 | 修改其他文件原文或把解析修订当正式改版 |
| 新增另一有效工程文件 | 独立确认其身份、范围和作用，补充事项依据 | 日期较新即替代全部旧文件 |
| 参考信息新增/修订 | 记录参考变化，按实际理解价值续接有关问题 | 自动改写受控要求或每次全事项重评 |
| 工程师纠正或发现AI误读 | 核对对应工作、来源和实际受影响字段 | 修改受控原件、默认所有既有判断无效 |
| 解析/语义修复 | 修正阅读产物，处理误读造成的实际分析影响 | 制造厂家新版本或全篇无差别重译 |
| 构型等原始事实更新 | 经正常证据链更新目标匹配及有关判断 | 把私人陈述或会议Closed状态直接当作完成事实 |
| 复看条件到期或满足 | 由已登记条件和现有消费者续接 | 仅凭自然语言“以后看看”宣称已自动监控 |
| 索引、图布局、普通页面刷新 | 修派生视图或读取 | 无故生成工程工作 |

已启动任务保留本轮范围，新变化进入后继；同一版本重复事件不重复派发。已发现变化、已取得材料、已选入、实际分析及已保存覆盖分别表达，不用“已同步”概括全链。

## 9.4 Aily讨论与贡献归集

Aily负责Host和飞书入口的自由交流。Host保存原话、作者、来源、时间、关注对象和必要上下文。来源明确、对象清楚且在原授权范围内的纠正或附件，由后台整理并在下一次获准更新中纳入；不要求逐条勾选、重复加入或反复确认。

普通术语解释、私人闲聊和单纯保存讨论不无条件重评。意图或对象确有歧义时再澄清；分享私人内容、扩大授权和正式业务决定保留必要确认。用户明确发起更新或已启用策略满足条件时，由Host受理真实任务。

Aily回答仍是派生解释，不能代替用户原话或根来源。跨入口可信回流、消息编辑/撤回和运行会话共享分别验收；人工粘贴的飞书摘录不能声称经过消息接口核验。群聊或同一智能体不天然意味着所有会话内容可互见。

正在运行时收到新指示，未接通平台实时干预就明确为后继处理。不能把消息已排队显示成模型已经读到。结果保存后Aily按权限读取确切新工作，普通业务版本变化不应永久禁用讨论。

## 9.5 Overall与当前阅读一致性

Overall基于准确JobAid/事项工作引用、有关原文和共同上下文，检查共同前提、相互冲突、措施覆盖、重要未知和本轮变化，不只压缩成员摘要。

问题工作更新后，本批直接受影响的综合及时更新。暂未完成时保留可读旧综合并说明其依据版本及未覆盖变化；默认知识使用带上这项限制。总体表示不能从多个latest自由拼接。

新问题、退役、风险依据或目标匹配变化，只处理实际影响范围。确需进一步分析就明确该部分尚未完成，而不是将所有旧问题重做一遍。

## 9.6 正式采用与专业重算

候选保存、阶段性完成、文件受理与正式采用不同。采用仍走现有权限、expectedRevision、来源核对和事务/CAS入口；外部正式审批、发布、实施和原始记录按各自系统承担。

构型证据采用后的适用性—JobAid—Overall重算复用既有专业链路。保存局部进度与正式提升结果分开，失败保留上一可用结果并说明覆盖。该数据支线不成为其他基于现有原文分析的共同前置。

# 10. 上下文、存储与读取接口

## 10.1 一个逻辑上下文，多种任务视图

共同上下文先于评估结果存在，复用文档、事项、来源、讨论、问题工作和执行记录。它不是每轮完整搬运的大JSON，更不是新建的上下文数据库。

| 内容 | Host保留什么 | 模型本轮取得什么 |
| --- | --- | --- |
| 对象与目标 | 文档/事项身份、范围、目标和真实时间 | 完成当前任务所需的业务范围，不含控制凭据 |
| 有效工程依据 | 精确源版本、现行核对信息、本版修订说明及来源入口 | 实际采用的文件内容与必要限制 |
| 参考和历史工作 | 完整索引、来源性质、工作引用和版本 | 选中的完整有用片段或论点，带参考用途 |
| 目标事实及陈述 | 原始来源、作者、有效时间、取得时间和核实状态 | 明确归因的事实或假设，不能混写 |
| 实际阅读 | 本轮交付的SourceRef、章节/记录范围 | 已读内容与可继续读取的入口 |
| 工程工作 | 完整问题、前提、未知、实际使用及变化 | 本轮相关的已有认识和更正 |
| 运行与正式动作 | 请求、租约、回执、采用和审批记录 | 必要的公开状态；控制标识由适配器持有 |

正文、实际依据、工作假设和已采用事实分开。初评、更正、Overall和Review复用同一装配语义，不能各拼一套材料使条件丢失。

下例是本文件整理的逻辑示例，不是已经部署的API字段定义，不要求新增同名表。开发应映射既有类型，避免与现有协议并行存在。

## 10.3 普通工作保存与索引事务

正文、真实业务版本/CAS及必要的已有projection pending登记在一个短事务中完成。事务提交后，以真实actor/tenant和精确工作引用重建索引；失败保留pending并可恢复，不复用已经结束的事务句柄执行异步SQL。

查询开关关闭不替代保存侧修复。pending登记不能只等索引失败后再写，否则进程退出可能丢失待处理意图。重建使用真实WorkItem或Matter身份，创建者/ACL owner不能冒充subject。

变化判定包含新增、修改、退役及影响当前阅读的顶层内容，排除trace和无业务含义时间噪声。`READ_ONLY`、实际用于判断和有依据的`NO_MATERIAL_CHANGE`分别处理，保留旧引用不证明本轮已经比较。

## 10.4 文件存储与读取

PostgreSQL保存业务记录、工作、讨论和状态；FileService保存原件、图片、完整解析包及较大产物。按访问方式组织数据，不将全部JSON搬库，也不强制所有JSON只能存文件。

存储模块登记SDK实际返回的位置及必要元数据，业务使用稳定DocumentVersion、SourceRef和artifactRef，不让每个模块猜默认桶或拼物理路径。上传、下载、字节处理和模型调用放在业务事务之外；必要业务登记采用短事务。

保留原有来源字节、产物传输完整性和权限检查，但不因反对新增hash平台就删除已有必要完整性校验。签名链接按需签发，不能成为永久地址。原件失联独立显示，不用缓存宣称当前源文件仍可读。

旧存储事故继续作为独立支持事项，不阻断新材料开发；不因新流程成功宣布旧事故解决。本批不新建恢复副本体系、同步双写、多后端自动切换或分布式缓存。

## 10.5 原文与翻译读取

Reader优先使用完整语义段、步骤和表格，保留准确原文映射；解析碎片不是翻译单位或工程问题单位。翻译块可对应多个源单元，不能为了旧UI强拆回碎片。

Translation V2持久保存已完成块和必要检查结果，允许部分先读。关键数值及对象关系、件号、单位、否定、条件、警告和范围需要保护；版式、语言等价变化与源文疑点分别处理，不只用数字集合判断质量。

**工程师无需逐块核对或确认译文才能继续工作。**可自愿修订译文并保留来源与版本；解释和疑点不混入原文翻译。局部表格限制只影响对应中文范围，原文可读的工程分析继续。翻译修订不自动作为新的独立工程证据。

复杂图、扫描页、跨页表和不确定脚注按实际能力显示限制；不能把模型估计位置说成精确坐标，也不假称所有文种已验证。

## 10.6 轻量首屏与局部展开

资料库用数据库执行授权范围筛选、搜索、稳定分页和快览，不依赖下载完整解析包。事项页先取得已有工作及准确状态，展开问题再取完整正文，点击依据再读相应原文。页面GET、刷新和hover不得启动LLM生成工作。

普通刷新保留当前可读内容、位置与草稿，仅更新变化部分；对象或授权变化时清理不再有权显示的内容。历史、讨论和材料分开按需加载，隐藏面板暂停无意义轮询。缓存绑定身份与版本，不能冒充FRESH_READ或掩盖原件不可用。

资料库保留目录/表格/快览、文档族与事项视图、机型/文种/ATA等实际分类。分类计数不等于适用机队数。全局入口与当前对象工具分组；lease、安装build和调试信息留在诊断，业务版本、未采用和未覆盖变化则直接可见。

保留原有体验目标作为测量目标而非发布关卡：正常已登录条件下核心首屏p50不超过1秒、p95不超过2秒；已加载同对象切换目标p95不超过100毫秒；轻量状态读取目标p95不超过1秒。首次授权、文件处理和模型时间另算，未实测不宣称达标。

## 10.7 外部来源与多格式

来源位置与业务文件身份分开。共享目录、厂家渠道、监管渠道、邮件和业务系统分别记录范围、获取方式、真实运行身份及最后成功检查；扫完六个文件夹不等于工程资料或SB/AD全覆盖。

分页正向观察对象、待受理意图和游标在现有持久机制中共同保存。已获准的新建/修改可以继续，完整遍历用于证明范围完整和谨慎处理负向缺失，不让一个不可读子树冻结全部正向变化。

改名、移动、行移动或修改时间变化不自动等于正式改版；稳定对象身份、实际内容及来源规则共同确定变化。原生表格保留记录ID、列名、selector、有效时间和取得时间，不为了统一解析全部转成PDF。未列出不等于删除，权限撤回与物理删除分开。

# 11. 开发协作、发布与清理

## 11.1 开发分工不进入产品运行链

M负责业务规则、关键修法、公共接口/事务、内容接受和发布组合。一个Luna复用既有CodeM入口，负责任务派发、回执初查和Git。CodeM执行客观取证、明确机械修改和定向测试，不自主制定工程结论或降低验收标准。P负责实际原文、语义和必要翻译局部质量；F/妙搭前端独立实施视觉与交互，M只统一读取含义与组合。

豆包当前不在关键路径。CodeM入口失效时做有边界恢复，仍失败则由M或已有脚本完成最小必要工作，不另建监督平台、不让业务停在“等待分流工具”。

## 11.2 技术发布按实际影响协调

| 变化 | 发布处理 |
| --- | --- |

当前为开发阶段，不要求长期双读、旧实验协议兼容或固定先后窗口。必要时正常收尾在途测试任务并一次切换；具体顺序由实际依赖决定。保留已获价值的原文、工作和来源引用，不为新协议伪造旧结构。

## 11.3 组合、Git与回退

前后端独立开发不等于可从不同旧基线整边覆盖。Luna核对实际提交、共同基础、接受范围及共享文件差异，M确认同一Host组合；服务端、schema、依赖锁和路由不因前端本轮未主动改动就自动视为无风险。
