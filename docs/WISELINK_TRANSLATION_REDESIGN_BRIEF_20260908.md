# WiseLink 翻译模块设计修订说明

供网页版 GPT 生成新的完整方案

日期：2026 年 9 月 8 日  
实施基线：WiseLink canonical Host，提交 `e9b353b0d`，已安装 Skill `r09.c43`  
文档性质：本次设计修订的任务书、事实依据和方案输入。本文明确重设计方向，不代表新的运行架构已经实现，也不把尚待评审的字段和阈值当作既定契约。

## 1 本次要解决什么问题

我们决定重新设计 WiseLink 的翻译模块。目标是让工程师能够及时阅读可信、可追溯的中文译文，在遇到模型服务故障、源文切分问题或局部翻译错误时，仍能保留有效进度并完成任务。新方案应兼顾工程内容正确性、可读性、运行稳定性、速度和维护成本。

当前方案能够完成翻译，但依赖原始解析单元的严格逐项对应、较长的串行模型会话以及多轮机械校验。一次后续调用失败可能使整次翻译结束，已经检查通过的译文片段无法有效接续。运行中不断增加纠正规则、提示词和预算，尚未解决这些结构性问题。

本次修订需要重新审视翻译的工作单元、上下文组织、原文定位、校验、进度保存、失败恢复和下游消费。请不要把现有实现当作必须保留的设计答案，也不要只在现有提示词上继续添加约束。应保留业务边界和有价值的基础设施，替换造成脆弱性的具体实现。

网页版 GPT 的任务是据此给出可评审、可实施的完整新方案。本文已经提供理解该任务所需的核心上下文；末尾附有可直接使用的提示词。

## 2 产品背景和翻译的职责

WiseLink 是围绕工程问题进行资料理解、评估和工程师持续协作的系统。当前材料主要包括英文航空工程文件，例如 Service Bulletin、Service Letter、技术通告，以及后续关联的受控资料。工程师需要阅读原文及译文、核对来源、理解条件和限制，再开展 JobAid 分项评估、综合判断和连续 Review。

系统的主要组成如下。

| 组成 | 当前职责 |
| --- | --- |
| 妙搭 Host | 身份和租户授权、文档及来源版本、WorkItem、ActionAttempt、事务与并发控制、候选保存及正式采用决定 |
| Hosted OpenClaw 和 Skill | 使用已配置的模型理解材料并生成候选，通过确定性适配器读取授权来源和提交结果 |
| Reader 和事项页面 | 展示原文、译文、进度、证据定位、候选判断和讨论，不自行推断权限或正式状态 |
| 外部业务系统和工程师 | 拥有原始业务事实及相应的正式审批、执行和采用权限 |

翻译模块提供受来源约束的中文表达，不能补写源文没有给出的工程事实、替运营商判断飞机适用性、作出实施决定或自动批准。术语解释、疑点说明和工程推断可以作为独立辅助内容，但不能混入译文并冒充原文。

原文始终是受控来源。译文应帮助工程师理解并回到相应原文核对，而不是成为另一个失去来源关系的事实库。

## 3 本次明确修订的设计原则

以下原则是新方案的方向。具体实现应由完整方案论证，不能直接把这些描述机械变成一套庞大的新状态机。

1. **分开原文解析粒度、翻译工作粒度和阅读定位粒度。** PDF 解析产生的碎片不是天然的翻译单位。翻译可以按完整段落、表格或其他有意义的内容块组织；原始 SourceRef 和定位信息继续保留。
2. **可追溯不要求译文逐碎片一一对应。** 允许一个译文块对应多个原始片段，也允许在有明确映射时进行更细的定位。不能用宽泛引用整页的方式掩盖实际映射缺失。
3. **已经验证的工作应能保存和恢复。** 普通模型调用失败不应默认抹掉整份文档的有效进度。恢复必须核对来源、任务和授权，不重放正式提交，不复活已取消的旧 attempt。
4. **区分翻译错误、源文问题、接口格式错误和服务故障。** 不同错误应有不同的处理方式。不能把上游服务错误统一当成模型不遵循，也不能把所有校验发现都当成同等严重的语义错误。
5. **校验以保护工程含义为目标。** 严格保护关键数字与其对象关系、件号、单位、否定、警告、条件、范围和限制；允许经明确规则确认的语言和排版等价变化。不能只用数字集合相同证明翻译正确。
6. **速度和稳定性是设计要求。** 应有首次可读结果、完整完成时间、纠正成本和故障恢复成本的度量；不能主要依赖持续扩大 token 或时间预算来维持运行。
7. **与实际消费者一起修订。** 新的译文结构、来源映射、Reader、结果保存和下游读取需要接通。不能只改模型提示词，随后再把新结果强行拆回旧碎片结构。

这些方向允许短文整篇翻译、长文按语义分块等不同策略。新方案应选择足够简单的主路径，而不是为每种情况建立独立子系统。

## 4 当前实现实际怎样工作

### 4.1 已观察的真实样本

当前主要运行样本为 `SB-787-31-0019-01.pdf`，页面登记编号为 `B787-81205-SB310019-00`。同一已上传文件被多个正常受理的评估任务复用，绑定同一 DocumentVersion，并非每次都创建新的文档版本。该解析结果包含 437 个内容单元和 438 条来源依据。

本文不附该文件全文，不把测试中的工程师假设当作实际机队情况。

### 4.2 当前数据和执行路径

```text
受控 PDF 和 DocumentVersion
    → 解析包及 sourceUnits / SourceRef
    → Host 领取翻译 ActionAttempt 并提供绑定输入
    → 适配器重建完整翻译输入
    → 同一原生会话理解全文，串行输出指定窗口
    → 按原始单元校验，必要时纠正失败单元
    → 全部单元完成后形成完整模型结果
    → 完整候选校验和受控交付
    → Host 保存双语产物及当前候选投影
    → Reader 和后续评估读取
```

有三种不同的分批机制，不能在新方案中混为一谈。

| 分批所在位置 | 当前用途 | 需要注意 |
| --- | --- | --- |
| Host MCP 输入交付 | 按约 14,000 UTF-8 字节的实际序列化大小分批交付来源 | 这是工具传输约束，适配器随后重建完整输入，不是翻译语义块设计 |
| 模型输出窗口 | 一般最多 96 个原始单元或约 6,000 个源字符；不在一个原始单元内部切开 | 这是输出工作预算，不是模型能力上限，也没有保证窗口恰好结束于完整段落或表格 |
| 完整结果交付 | 完整模型结果及校验之后，通过已有提交机制交付 Host | 已有交付分片不能等同于模型生成过程中已保存可恢复的译文进度 |

模型最初获得完整源文和规则输入。后续请求通过同一原生会话继续，适配器主要发送新的工具交换和窗口指令，而不是每轮在请求体中重新拼接整份源文。原生会话历史仍持续保留全文、输出和纠正过程，实际模型上下文和处理成本会增长。不能简单把耗时归因于“客户端每次重复发送全文”，也不能假定会话复用没有上下文成本。

### 4.3 当前输出与校验约束

模型输出采用带索引的 `translatedUnits`。每个索引必须翻译自己的原始片段，包括跨片段句子的一部分。提示词明确禁止跨索引移动、合并、借用、遗漏或重复内容。

Skill 和 Host 共同执行既有翻译规则。其中数字保真按单元比较 token 及出现次数；日期、中文相邻数字和部分标识串已有专门处理。每个输出窗口最多进行两轮批量纠正；满足收敛条件时，少量残余单元可继续逐单元纠正。全部内容最终仍要通过完整校验。

Host 当前双语产物以 `source.unitKey` 查找候选译文，再为每个原始单元保存 `sourceText`、`translatedText` 和 `sourceRefIds`。因此，逐单元对应不仅存在于提示词，也存在于当前数据契约和消费结构中。新设计如改变粒度，必须说明 Host 产物与 Reader 的兼容和迁移。

### 4.4 当前预算与失败收尾

- 翻译模型调用及其纠正共享最多 45 分钟预算，单响应最多 15 分钟；每轮开始前续租原 Host attempt。
- M3 当前按既有用户授权申请 524288 completion tokens。该值是请求配置，不代表实际输出都使用了该额度，也不证明能以此获得稳定吞吐。
- 模型服务通过现有官方 Hosted profile 路由；本次不要求改用其他外部模型服务。
- Review 已有针对明确临时 HTTP 错误或连接建立前失败的有界重试，不能据此宣称翻译也已具备同样的重试能力。
- 翻译窗口的校验记录会持久保存，但通过校验的译文片段当前主要积累在本次模型调用内部；完整 `model.result` 要等全部窗口完成。
- 整个模型生成过程被包在一个远程步骤中。若只有 started 记录而没有 result，既有通用 checkpoint 逻辑会将结果视为未知；翻译没有可供正常产品流程使用的分块恢复协议。
- 发生提交前执行错误时，消费者通常取消当前 attempt 并保存失败记录。已失败阶段不会被下一次自然 tick 自动重放。现阶段排障后多次采用新建评估任务重新验证，代价较高。

## 5 真实运行证据说明了什么

以下是不同运行的样本记录，不是受控统计实验，也不足以计算稳定成功率或判断某个模型普遍优于另一个模型。所有时间均为 2026 年 9 月 8 日北京时间。

| 运行 | 观察结果 | 能支持的结论 |
| --- | --- | --- |
| M3 11:22:43 至 11:29:54 | 437 个单元全部通过并保存，约 7 分 11 秒 | 模型与当前链路能够完成该材料；不能仅因后续 JobAid 失败就说翻译失败 |
| M3 20:17:56 至 20:32:52 | 翻译成功，约 14 分 56 秒 | 成功运行也可能需要较长时间，且不同运行的成本有明显差异 |
| DLI 20:55:25 至 21:10:04 | 翻译成功，约 14 分 39 秒 | 翻译能力并非 M3 独有；没有足够样本给两模型排名 |
| M3 21:35:06 至 21:42:44 | 前三窗推进至 276 个单元；最后成功窗为索引 180 至 275，保真发现为 0；下一响应上游 `server_error`，输出为 0，整次翻译取消 | 这次主要是上游服务故障及恢复机制不足，不能归因于译文不遵循要求 |
| DLI 22:11:20 至 22:24:45 | 翻译成功，约 13 分 25 秒，随后自动进入 JobAid | 最新一次也能完成全文，但不能由一次成功证明生产稳定 |

另有两类历史证据值得保留：

第一，早期运行中同时发现过日期与中文相邻数字的校验误判、真实漏译，以及相邻单元数字或标识串移。校验器曾需要修订，模型输出也确实存在错误。这说明不能把全部拒绝都解释为模型差，也不能把全部校验都取消。

第二，旧 Node fetch 的独立响应头等待上限曾使调用在约 300 秒中断，早于业务操作预算。该传输问题已有对照实验和核心 HTTP 调用修复。它属于已修复的客户端问题，不应在新方案中继续误称为模型全局 300 秒限制。

最近 M3 上游 `server_error` 在原生记录中可见，但适配器收到的模型接口响应表现为 HTTP 200、无可用工具输出，最终报告 `INITIAL_OUTPUT_CHANNEL_INVALID`。新方案必须讨论可靠的错误分类和传播，不能简单对所有 HTTP 200 空输出盲目重试，也不能只在自然语言错误消息上写脆弱的匹配规则。

JobAid 曾发生的 JSON null / 数组序列化问题、单行预算问题是另一个阶段的故障。它们解释了部分完整初始分析未完成的原因，但不是翻译质量或翻译耗时的直接证据。

## 6 对现状的设计判断

| 问题 | 当前事实 | 设计上的影响 |
| --- | --- | --- |
| 原始切分被当成语言边界 | 译文必须保留每个原始片段的索引归属，跨片段内容不能重组 | 模型同时承担翻译和碎片切分服从任务；自然中文表达与定位约束容易相互牵制 |
| 校验粒度和错误等级不够合适 | 数字与出现次数等检查在细粒度单元上执行，局部发现会触发纠正流程 | 容易为碎片边界或等价表达支付多轮生成成本；同时仍不能证明语义关系正确 |
| 工作进度和最终结果没有充分分开 | 通过窗口的校验记录可见，译文内容未形成可恢复的持久工作产物 | 服务故障可能使有效生成工作无法复用，恢复成本接近重新开始 |
| 生成和正式提交使用了过于相似的失败处理 | 纯候选生成步骤也被整体封在 started / result 的通用远程步骤中 | 保护提交不重复是必要的，但不能直接替代可恢复的生成协议 |
| 观察指标不足以解释耗时 | 运行报告的 `modelCallCount=1` 可能表示调用了一次适配器，内部实际有多轮模型响应 | 用户和开发者难以分辨生成、纠正、工具传输、等待和提交分别耗时多少 |

我们的结论是：来源可追溯、受控版本和正式采用边界应继续保留；当前把这些目标落实为逐碎片翻译和整次失败收尾的方式需要修订。不能把“保护来源”当作保留所有现有耦合和阈值的理由。

## 7 新方案必须保留的边界

这些是业务与安全边界，不是对现有实现细节的冻结。

1. Host 继续管理身份、租户和 actor 授权、文档版本、来源绑定、事务和并发更新。前端、模型和原生会话记忆不代替 Host 当前事实。
2. 原文与译文、受控来源与生成候选、工程师修订与模型输出必须可区分。译文疑点或解释不得冒充原文。
3. 使用当前已经配置并授权的官方 Hosted 模型路由。模型由用户或任务设置选定；恢复不能静默切换到另一模型、另一数据接收方或另一权限范围。
4. 模型输出保持候选。翻译保存和工程师修改不自动构成适用性确认、工程结论正式采用、批准或实施决定。
5. 保存和恢复进度不能跨租户泄露，也不能在源版本、翻译策略或有效授权变化后无条件复用旧内容。模型变化如何影响复用应有明确规则和可见记录。
6. 提交结果未知时先核对原结果，不盲目重复正式写入；已取消或失败的 attempt 保留原历史，不改写为成功，不通过修改数据库状态复活。
7. 翻译遗漏、源文无法辨认和未完成范围必须可见。允许局部译文先供阅读，但不能把部分完成标成全文完成或供下游误当完整依据。
8. 沿用已有数据库、对象存储、主键、版本、事务、唯一约束和权限设施。需要新记录类型时说明具体失败场景与职责，不默认增加第二套业务数据库、大型工作流平台、全新哈希体系或层层 gate。
9. 保留旧失败和存储事故记录；开发仅向妙搭 Host 的 `origin` 推送。此文档本身不授权向其他系统发送项目资料或进行正式业务采用。

## 8 完整新方案必须回答的问题

### 8.1 翻译工作单元与源文整理

如何从段落、标题、表格、警告、列表、脚注和跨页续文中形成工作单元？哪些整理可由确定性程序完成，哪些需要模型或工程师参与？如何保留未经修改的原文和整理理由？源解析质量不足时，问题应退回解析、局部重读页面，还是进入翻译待核状态？

必须区分恢复阅读顺序、连接排版断行与改变源文事实。不能让模型静默修正 OCR 后把推测当成原文，也不应迫使翻译保留明显不属于语言结构的排版碎片。

### 8.2 对齐和来源定位

请定义解析片段、翻译块、译文段落和 SourceRef 之间的关系，并给出一个跨三个原始片段组成完整段落、另一个跨页表格的示例。说明原文到译文、译文到原文如何定位；能够精确到什么程度，不能精确定位时怎样显示。

考虑段落调整、表格脚注、双向滚动、高亮、复制和导出。不要要求模型生成它无法可靠验证的坐标或字符偏移；也不要为了继续使用旧 Reader，就把合并译文任意切回原始碎片。

### 8.3 全文理解和上下文成本

如何在有完整理解能力的前提下避免无限增长的会话？请比较完整文档上下文、稳定术语与文档结构信息、局部相邻内容、按需读取交叉引用等方式。说明何时使用何种策略，如何避免丢失远处的例外、定义或适用条件。

需要保留本次任务的整体覆盖目标，不能只挑容易翻译的片段。也不能用未经核对的模型摘要替代源文细节，或让不同并行块对同一术语和警告产生不一致表达。

### 8.4 模型调用和结构化产物

请给出最小输入输出示例、术语约束、表格表达和错误返回方式，说明哪些字段由模型生成，哪些标识、来源绑定和版本由确定性程序填写。考虑长输出截断、空输出、无效 JSON、错误的工具参数类型和不同已授权模型的格式表现。

当前采用过 JSON 字符串参数来避免某些嵌套数组和 null 的序列化问题，这是可复用经验，但不要求把所有模型都锁死在同一临时补丁上。输出限制、窗口大小和纠正预算应基于实际接口、材料规模与测量结果，不使用未经验证的万能固定值。

### 8.5 保存进度与恢复执行

请明确“已生成”“已校验”“已持久保存为工作进度”“可供局部阅读”和“全文候选已提交”的区别，尽量复用现有状态和记录。

必须给出以下情况的具体恢复顺序：服务返回明确临时错误；请求结果未知；进程在保存块前后退出；Host lease 丢失；总预算耗尽；用户取消；源版本变化；最终提交结果未知。

说明恢复复用什么、不复用什么、怎样重新核对绑定，以及何时继续原 attempt、何时需要一个正常的新请求。重点是恢复同一评估的有效工作，不再让用户为了一个失败窗口重新创建整份资料评估。候选生成可恢复和正式提交不重复应分别设计。

### 8.6 翻译质量和校验等级

请为不同检查定义目的、适用粒度、误判风险、处理结果和解释方式。至少包括：

- 内容覆盖和真实漏译；重复内容及必要的重复警告。
- 件号、标识符、数值、单位、正负号、范围，以及它们与对象、操作和条件的关系。
- 否定、例外、条件、强制或建议语气、时间要求和适用范围。
- 日期等价表达、中文数字相邻、跨行标识、表格单元格和脚注归属。
- 术语一致性、中文可读性，以及原文存在歧义或 OCR 不确定时的标记。

请说明哪些错误阻止该块用于受控消费，哪些可以保存为带疑点的候选、只限制局部用途，哪些仅是提示。局部疑点不能隐藏，也不应无差别阻断无关内容。单纯数字 token 集合相等不能作为语义正确性的充分条件；增加一个“审校模型”也不能被当作自动可靠的保证。

### 8.7 与 JobAid 综合评估和 Review 的关系

请核对哪些消费者真正依赖译文，哪些本来可以直接读取受控英文来源。不要未经分析就把整份中文译文完成设置为所有工程分析的强制前置，也不要未经说明就解除现有依赖。

方案应说明可并行的工作、需要完整译文的工作、使用部分译文时的限制，以及翻译修订对既有评估和 Review 的影响。工程判断仍须绑定实际读取的来源；翻译本身不能成为独立的原始工程事实来源。

JobAid 的原文解读、综合分析方式、有限外部信息下的调查与连续评估已独立整理为[JobAid 评估流程修订说明](WISELINK_JOBAID_ASSESSMENT_REDESIGN_BRIEF_20260908.md)。本翻译方案在此核对共同上下文、来源读取、局部变化和下游依赖接口；两份方案须保持这些接口一致。

### 8.8 工程师体验

请描述正常用户操作：打开资料、何时看到第一段译文、何时可阅读大部分内容、发现疑点如何返回原文、如何只重译或修订相关内容、服务故障后如何继续、如何区分未完成和失败、如何了解本次修改影响范围。

进度应反映真实工作量和阶段，不能用模型请求次数伪装完成百分比。面向工程师的页面不需要暴露 lease、工具参数、JSON、checkpoint 文件或内部服务配置。

### 8.9 可观测性与成本

最少应能分辨解析整理、首次生成、纠正、等待服务、进度保存和最终提交的耗时；区分适配器调用次数、实际模型请求次数、纠正次数和恢复次数。记录已授权接口可可靠提供的输入输出 token、字节和费用信息，缺失时明确缺失，不重复累加汇总记录。

请提出可验证的性能目标及采样方法，明确它们是建议验收目标而非既有成绩。当前少量成功与失败样本不足以支持“成功率 99%”或固定分钟数的承诺。重试应受总成本、时间、并发和服务限流约束，不能形成无上限循环。

### 8.10 兼容和迁移

说明旧逐单元双语产物、新翻译块和既有工程师修订怎样并存与读取。哪些旧译文可以复用、如何验证、哪些必须重新处理，不能一律重跑历史材料，也不能把旧失败记录改成新成功。

必须列出 Host、Skill、shared/API、Reader、持久化和下游消费者的改动范围、兼容顺序、回退方式及旧代码移除时点。若声称无需修改某一层，需要解释真实消费者如何适配新的粒度与状态。

## 9 方案取舍的要求

请比较少量有实际意义的架构选项，例如短文整篇生成后对齐、按语义块有界生成、具有全文规划和局部恢复的混合方式。对比重点应是上下文完整性、对齐可靠性、失败恢复成本、延迟、模型调用成本和实现复杂度。

最终必须选择一个清晰的主方案，给出短文、长文和复杂表格等情况的适用规则。不要把所有备选项都同时实现，也不要默认每个解析碎片都需要单独调用一次模型。若建议并行，说明并发上限、顺序依赖和术语一致性；若建议串行，说明为什么不会再次形成过长的会话和高昂的重做成本。

## 10 必须覆盖的验收场景

以下是测试场景，不是具体航空工程结论。测试中的构造文本应明确标记为测试数据；实际运行仍需使用授权真实材料。

| 场景 | 应能验证的行为 |
| --- | --- |
| 一个完整句子跨多个 PDF 片段 | 译文自然完整，能定位全部相关原文，不因碎片边界强迫语义断裂 |
| 跨页表格和延续表头 | 行列关系、单位、脚注和适用条件正确，不丢失后页续表内容 |
| 相同数字属于不同对象 | 检查能发现对象或条件关系串移，不能仅靠数字总数相同通过 |
| 日期等价写法和中文紧邻数字 | 合法表达不会被机械误判；真正日期或数值变化仍被发现 |
| 件号或术语受 OCR 粘连影响 | 不静默编造修复；能保留原文并标出具体待核位置 |
| 否定或例外只出现一次 | 不能在生成、压缩、纠正或跨块复用时丢失 |
| 关键警告与普通版式问题同时存在 | 严重性和处置范围不同，工程师能看到原因 |
| 某一块收到明确临时服务错误 | 其他已验证进度保留；符合授权和预算时只恢复受影响工作 |
| HTTP 200 但没有候选或上游错误被包装 | 有可靠分类和可见诊断，不冒充成功，不对任意空响应无限重试 |
| 进程在块保存前后分别退出 | 可判定有效进度，不重复或丢失已保存块，不产生重复正式提交 |
| 最终提交响应丢失 | 核对原提交结果，避免再次创建同一正式候选结果 |
| 恢复前源版本或有效权限发生变化 | 重新授权和核对绑定，拒绝不适用的复用 |
| 用户取消后再次正常请求继续 | 原取消记录保留；新请求通过正常入口恢复可复用工作 |
| 局部疑点未闭合但其余块已完成 | 可阅读部分的范围和限制清楚，全文完成及下游消费状态不被夸大 |
| 工程师修改一个术语或一段译文 | 修改记录可追溯，影响范围明确，不无理由重译整份文档 |
| M3 和 DLI 分别运行同一真实材料 | 分别测量质量、时延、纠正和恢复，不以换模型成功代替指定模型验收 |

验收应同时覆盖内容质量、运行恢复和真实页面使用。已有的单元测试、结构校验和一次成功运行不能替代连续真实样本证据。请提出合理规模的验证集、失败注入、人工抽查方法和阶段性上线条件，并说明哪些指标需要上线前测量后再确定。

## 11 期望网页版 GPT 交付的完整方案

请交付一份可以让后续开发者直接拆分实施工作的方案，至少包含：

1. 对当前问题的独立判断，区分已证实事实、设计推断和仍需验证的假设。
2. 主要方案选择及关键备选的取舍，说明保留、替换和删除哪些旧设计。

5. 执行、纠正、超时、取消、恢复和提交未知的处理表，明确 Host 与 Skill 的责任。
