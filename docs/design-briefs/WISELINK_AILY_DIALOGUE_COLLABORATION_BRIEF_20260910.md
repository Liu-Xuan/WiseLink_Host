# WiseLink：Aily 持续对话、工程上下文归集与 OpenClaw 重新评估——深入设计任务书

日期：2026-09-10（Asia/Shanghai）  
用途：上传给网页版 GPT，作为独立背景材料，进一步研究产品交互、平台能力与架构方案。  
状态：设计分析输入，不是已实施方案。本文明确区分用户已确定方向、当前实现事实、待比较的设计假设和待核验的平台能力。无需读取代码仓库或此前聊天，也应能完成分析。

## 1. 给分析者的任务

请基于本文，为 WiseLink 设计完整的 Aily 自由对话与工程评估协作方案。不要只复述三组件分工，也不要先围绕现有表结构修补。先从工程师实际工作与最低交互负担出发，比较方案并给出明确推荐，再落到对象模型、数据流、权限、并发、API 能力验证和分阶段落地。

重点解决：用户在飞书里可以持续、跨工程对象与 Aily 交流；有价值的信息如何准确、可追溯、低负担地回到 Host 的相应文件和事项；Host 页面内的对话如何与飞书协调；多人如何协作；Host 初始分析与新工作版本如何及时供 Aily 使用；何时、由谁、按什么范围触发 OpenClaw 重新评估。

请主动挑战本文的“候选方案”，但保留用户已确定的产品方向和业务权威边界。平台能力未知时给出验证方法与条件方案，不能将未知接口写成现成能力。

## 2. 用户原始诉求与已确定方向

用户已明确：

> 自由对话使用 Aily，初始分析、自由交互后的重新分析都是 OpenClaw。这样 Aily 一直负责自由交互，可以在 Host 上完成，也可以在飞书中完成。且 Aily 的响应速度更快，用户体验更好。

本次进一步要求：

> 用户可以在飞书界面使用 Aily 持续对话，但如何区分不同的工程对象。如果为了最佳体验，其实自由对话可能是不区分的，但对话的相关信息、结论，如何返回 Host，如何拆分进入相应的工程文件、事项的评估上下文，如何触发 OpenClaw 的重新评估。用户在 Host 复核评估界面中用 Aily 的自由交互与在 Aily 中的交互如何协调处理。不同用户对相同工程文件、事项的交互如何协调处理。Host 生成的初始分析、评估上下文如何让 Aily 使用，加入知识空间吗？都需要细化分析。

确定的角色分工：

| 组件 | 目标职责 |
| --- | --- |
| Aily | 持续自由对话、检索、解释、追问、澄清、帮助组织线索；Host 与飞书均可作为入口。 |
| 妙搭托管 OpenClaw | 初始分析、用户明确发起的重新分析，按工程方法生成结构化候选和工作判断。 |
| WiseLink Host | 工程对象、文档与来源版本、身份授权、讨论与材料记录、分析请求、候选版本、正式采用及并发控制。 |

“更快”是体验目标与用户判断，目前没有同条件延迟测试结论。设计应减少自由聊天经过 OpenClaw 调度和二次生成的环节，并给出测量方法。聊天保存、上下文选入、工作评估更新与正式采用是不同动作，不能统一成一个“确认”。

## 3. WiseLink 是什么

WiseLink 是围绕工程问题的上下文评估与工程师协作系统，当前业务背景包括航空工程文件、服务通告（SB）、服务信函（SL）、问题调查材料及相关技术资料。它帮助工程师理解问题现象、机理、调查进展、临时与最终措施、实施前提、运营影响和发布里程碑，并按 Job-Aid 等方法形成分项与综合判断。

典型流程：工程文件进入系统 → 解析与翻译 → 适用性、Job-Aid、综合初始分析 → 工程师阅读材料并与助手讨论、补充或纠正信息 → 明确发起更新评估 → 生成可审阅的新工作版本 → 按已有权限与正式入口采用。

背景不完备仍可分析：应指出未知及其对判断的影响，而不是要求所有缺口清零。背景知识可以辅助解释与候选判断，但不能自动证明本机适用、构型事实、措施已执行或已经批准。

### 3.1 必须分清的业务概念

| 概念 | 含义与边界 |
| --- | --- |
| 工程文件 / DocumentVersion | 文件身份与具体版本；同一文件可能被多个事项使用，不等于某个事项的判断。 |
| 工程事项 / WorkItem | 当前评估对象及其业务条件、权限和版本；文件相同不代表事项相同。 |
| 工程问题脉络 | 跨文件的现象、机理、调查与措施演进；可跨事项，首版不要求建立全量知识图谱。 |
| SourceRef | 可追溯的原文或材料引用；模型写出的标题或链接不自动成为已核实 SourceRef。 |
| 讨论记录 | 工程师输入与助手公开回答；可能包含事实陈述、猜测、反例、纠正、建议或任务意图。 |
| WorkingAssessment | 可继续修订的工作判断；不等于正式采用的业务结论。 |
| ReviewAction / 正式采用 | 独立的受控业务动作，保留现有授权与确认边界。 |
| ActionAttempt | 一次分析执行的持久记录，承载真实运行状态、输入与产物关联。 |

一个讨论片段可以同时对多个对象有价值，但在不同对象中的贡献、适用条件、可见范围和接受状态可能不同。

### 3.2 必须保留的边界

Host 管理身份、租户与 actor 授权、来源、版本、事务与并发更新；外部系统仍拥有其原始业务事实和正式审批/执行记录。模型输出是候选，不自行批准、放行或正式采用。普通线索归集和工作候选更新不应被设计成逐项正式审批。

产品运行使用已配置的妙搭官方 Hosted profile。不能把开发者电脑、个人 CLI 凭据或 Codex 管理会话当作团队用户的生产运行路径。不能因为开发者能读某个知识空间，就认定全部业务用户都能读。

## 4. 当前实现事实：新分工尚未迁移

以下是截至本文日期的本地代码与运行记录快照，不是目标架构：

- 当前 Host 普通发送仍产生 CHAT，由 Hosted OpenClaw 执行，必要时调用 Aily 检索工具。普通讨论不自动重算 JobAid/Overall。
- 用户点击“更新评估”时，Host 会保存选中的讨论范围、材料及基线，交 OpenClaw 生成工作更新。选择范围已经有页面与持久记录实证；完整更新业务循环仍存在失败，不能写成已验收。
- `ReviewConversation` 当前包含 tenant、actor、WorkItem，并绑定 OpenClaw session；现有唯一范围是 tenant + actor + WorkItem。它不是跨用户、跨对象的统一会话模型。
- `ReviewTurn` 当前绑定单个 WorkItem，记录输入、公开回答、引用、候选、复核范围和执行关联。直接把跨对象飞书会话塞入此表会遇到语义不匹配，需设计适配。
- Aily 接入已完成用户 OAuth 的 write 权限正常授权，以及 POST 流式响应在 Host 中持久保存公开文本、状态和本地轮询。实现使用 `/open-apis/aily/v1/agents/{agent_id}/chats`；当前内部 query 绑定 actor、tenant、身份 session 与 ActionAttempt。
- 该身份 session 不等于 Aily 对话 session，也不等于 ReviewConversation，更不能与飞书 chat_id 混为一谈。现有 query 结构仍为 OpenClaw 内部检索调用服务，不是已完成的长期自由聊天存储。
- 传输实现保留部分响应；无法确认完成时标为 UNKNOWN，不将断流当作成功，也不因轮询自动再次发起远端调用。
- 实际 CLI 用户身份对话返回过成功的公开文本；Host 新业务回合在调用检索 MCP 时失败，未登记 query。只读取证表明模型生成了工具调用，但失败发生在取得业务结果前，原始错误不足以确定是 MCP 传输还是 Host 登记前拒绝。不能将传输修复写成 Host 业务检索闭环已成功。
- 尚未实现：Host 自由聊天直接路由 Aily、飞书原生对话可信回流、跨渠道会话关联、跨对象归集、团队共享协作与评估结果回供 Aily。

实现定位：`server/database/schema.ts` 中 reviewConversation、reviewTurn、reviewAilyQuery；`server/modules/canonical-host/review-aily.service.ts`；`canonical-host-engineer-review.service.ts`；`canonical-host-openclaw-review.service.ts`；`canonical-host-common-context.service.ts`。这些路径只是后续实施索引，不要求网页版分析者读取。

## 5. 核心设计问题：聊天连续性与工程归属应如何分离

请比较三种方案，而不是默认选择其中一种：

| 方案 | 体验与收益 | 主要代价或风险 |
| --- | --- | --- |
| 每个事项独立聊天 | 上下文边界清楚、易归档 | 飞书里频繁切换；跨对象推理不自然；一段话涉及多对象时处理困难。 |
| 每人一个持续跨对象聊天 | 最接近自由助手体验 | 对象指代、私密范围、历史陈旧与上下文污染更难；不能把所有聊天自动放入所有事项。 |
| 连续聊天 + 显示当前关注对象 + 后台归属候选 | 保留自由交流，又能在必要时校正对象 | 需要设计可理解的焦点变化、片段归集和纠错机制。 |

可供挑战的初步假设：用户界面允许自由聊，不强制每条消息选择事项；Host 维护可纠正的对象关联。聊天线程、运行 session、工程事项上下文分别建模，不能用一个 ID 代替全部概念。

需要回答：

1. 用户首次没有对象时是否正常回答？何时仅做一般解释，何时加载 Host 资料？
2. 如何识别文件号、Host 链接、版本、机型、设备或构型条件、事项名称和“刚才那个”等指代？文件精确命中后，如何避免误选同文件的另一事项？
3. 当前焦点是单一对象、多个对象还是无对象？由显式选择、页面位置、最近讨论或模型建议中的哪些信号决定？切换后怎样让用户看见？
4. 什么时候可以自动建立可撤销的候选关联，什么时候需要短澄清？置信度能辅助排序，但不能替代对象身份或权限检查。
5. “Win10 只是测试假设，实际是 Win7”如何撤回前提并影响已经归集的内容？不是再保存两条同等有效的事实。
6. 新谈及的文件尚未入库或事项尚未创建时，如何留存线索，而不凭空创建正式工程对象？
7. 同一个跨事项解释哪些部分属于一般背景，哪些只适用于对象 A，哪些是 A 与 B 的比较？

## 6. 从对话到 Host：建议研究的归集链路

候选链路：公开原始消息 → 可引用片段 → 对象关联候选 → 可用于评估的上下文增量 → 一次明确的重新评估输入 → 新工作判断。

每一步都需说明：触发者、同步时机、持久内容、权限、可撤销性、失败反馈。不要以一份 Aily 总结替代原话，也不要把全部聊天全文无差别加入每次评估。

### 6.1 最小语义与溯源要求（逻辑字段，不是定稿数据库）

- 原始消息：可信发送者、租户、渠道、原始消息标识、会话标识、时间、公开内容或可访问引用、编辑/撤回状态；拿不到原文时明确是用户提交的摘录或总结。
- 讨论片段：对应消息及具体范围、必要的前后问答、作者与助手角色、提取时间；区分用户陈述、模型解释、待证假设、反证、纠正和建议。
- 对象关联：目标文件及版本、目标事项、相关评估点或问题、关联理由、适用条件、建议者/确认者、候选或已选入状态；允许同一片段有多个不同关联。
- 可见性：原消息权限、目标事项权限、共享授权或共享策略；目标事项成员资格不自动赋予阅读源材料的权利。
- 来源与变化：外部材料身份/版本、是否已读取核实、修订或撤回关系；模型总结仍指回原话和材料，不升级为原始证据。
- 使用记录：在哪次评估的输入范围中使用、产生何种影响、何时被后续信息取代。引用同一来源的多个摘要不算多个独立证据。

请评估哪些可复用现有讨论、SourceRef、材料记录与版本机制，哪些确实需要新增实体。不要为了完整而建立另一套业务数据库或复杂通用事件平台。

### 6.2 自动化与用户控制

请明确区分四种动作：保存聊天、建立可撤销关联、把内容分享给事项参与者、发起评估。它们不必都弹确认，也不能因一次聊天授权就自动等同于全部四种授权。

请设计低负担反馈，例如回复末尾显示“这段讨论关联到事项 A，可调整”；私人内容转为团队可见前给出范围提示；“用于更新评估”时一次查看对象与重要新增信息。具体是否采用这些交互由分析结论决定，避免每轮都出现卡片和弹窗。

## 7. 两个入口如何协调

### 7.1 Host 复核页面

Host 页面天然知道当前 WorkItem、文件版本、选中的评估点和材料。Aily 应能承接这些信息，但用户仍可能在页面内追问其他文件或一般问题；页面位置是默认焦点，不应强制所有发言归属于当前事项。

需设计：加载了哪个工作版本、哪些讨论来自飞书、哪些已用于上次评估、哪些尚未使用、其他人新增了什么。进入页面时不应无提示地将用户的整个私人 Aily 历史变成团队可见。

### 7.2 飞书 Aily 页面

用户希望自然连续交流，可以通过文件链接、对象卡片或主动选择聚焦事项。请核实原生渠道究竟可获取哪些事件、对话消息、用户身份、附件与上下文，是否能安全调用 Host、展示卡片或跳转。

若平台不能共享底层 session，是否采用“各渠道独立运行会话 + Host 提供当前上下文和必要历史增量”？用户可感知的连续性是否一定需要完整逐字镜像？哪些历史应按需取回，哪些只需说明摘要与来源？

### 7.3 双入口同时使用

必须覆盖：Host 与飞书几乎同时提问、重复回调、乱序事件、回复中断、消息编辑撤回、同一答复经另一个入口回流造成循环。提出普通唯一键、顺序标识和版本机制即可，不默认引入复杂分布式锁。

区分“消息送达”“Host 已保存”“对象归集完成”“评估已请求”“工作版本已更新”。不要用一个绿色成功状态覆盖整条链路。飞书聊天已回答而 Host 回流失败时，用户需要看见可恢复状态，系统不能静默丢失，也不能自动重复生成答案。

## 8. 多用户对同一对象如何协作

请分别设计个人助手记忆、事项共享讨论、可供共同评估的材料、分析候选及正式采用记录。不要给多个用户复用一个含私有历史的模型 session。

至少分析以下情况：

- 甲私下提出假设，乙在同一事项页面工作：乙何时能看到？自动归集是否只形成甲的私人待整理项？有没有团队可配置的默认共享模式？
- 甲与乙对同一前提给出矛盾意见：保留作者、依据、范围与时间，不能最后写入者覆盖，也不能让模型投票决定事实。
- 两人同时基于工作版本 3 发起重评：采用排队、复用同一输入任务、保留并行候选还是要求重取基线？不同输入不能只因目标相同就去重。
- 甲的评估运行期间乙补充新材料：已启动任务应保留原输入范围；新材料是否提示“未包含”，是否建议后续更新，而不是悄悄改变正在计算的输入。
- 用户退出项目、文档权限撤回、群成员变化：新的读取和生成须重新判权；既有会话记忆不能因工具权限收缩而自动视为已清除。
- 一个结果引用了只有甲能看的材料：是否允许分享、如何获得授权、能否生成有依据的受限摘要；不能默认摘要就是无敏感信息。
- 原生 Aily 群聊与私聊是否同一阶段支持？群内可读不代表可转发给另一个事项的全部成员；群中提到人也不构成该人的操作授权。

需要推荐默认协作策略，同时说明可配置范围、治理成本与界面负担。允许工程师分歧和多个工作候选，不要求所有讨论先达成共识。

## 9. 如何触发 OpenClaw 重新评估

既定方向是用户明确发起重新分析。请区分系统建议“值得重评”和实际创建执行请求；新消息、新知识命中或普通归集本身不应无条件启动昂贵分析。

请设计 Host 按钮与飞书自然语言请求的统一行为。例如“用我们刚才讨论的内容更新这两个事项”，系统如何解析目标、显示范围、处理歧义，并在已明确授权的范围内执行，而不重复追问已表达清楚的意图？

一次请求需要明确：目标事项与版本、基线工作版本、选用讨论片段及纠正关系、材料及来源版本、未核实前提、更新范围、请求者及授权、幂等标识。原始讨论与材料可按需读取，不能只传 Aily 的结论。

请比较局部重评与完整重评：改变一个实施前提时，怎样确定受影响评估点并检查综合结论的一致性；如何避免把局部变更漏传给整体判断，也避免每次重新翻译和重做全部分析。

请给出从请求到候选可用的状态流程，包含排队、执行、失败、结果过时、取消、重试及结果回供。成功结果应说明输入截止范围、关键判断变化与剩余未知；失败保留上一可用工作版本并给出具体恢复方式。新的工作候选与正式采用继续分开。

## 10. Host 的分析和上下文怎样供 Aily 使用：是否加入知识空间

这是本次需要深入比较的问题，不能直接回答“全部放入知识库”。请至少比较：

| 方式 | 适合解决什么 | 必须处理的问题 |
| --- | --- | --- |
| 每轮附带精简上下文 | 页面已知对象、快速进入当前判断 | 输入预算、裁剪依据、重复传输、旧摘要、多个对象混淆。 |

## 12. 要求覆盖的端到端场景

以下是虚构设计场景，不是新增业务事实：

1. **无对象开始**：甲在飞书讨论“Windows 升级对维护工具的影响”，之后提供文件 A 链接。开始阶段可一般讨论，识别对象后只归集相关片段。
2. **跨对象比较**：同一段对话比较文件 A、文件 B 和两个不同构型事项；系统不能将 A 的措施或假设复制为 B 的事实。
3. **纠正前提**：甲声明此前 Win10 是测试假设，实际是 Win7；需要沿用与撤回哪些片段，上次评估是否需要提示复看？
4. **Host 接续飞书**：甲打开事项 A，看到来自飞书的相关讨论，继续追问并发起更新；无关私人对话不出现。
5. **飞书接续 Host**：初始分析刚完成，甲在飞书问“上次说的风险现在怎样”；系统消歧事项并说明当前工作版本和未知。
6. **多人分歧**：甲认为需要措施，乙提供相反材料；两种意见及来源并存，模型解释分歧，不能擅自确认业务结论。
7. **并发重评**：甲乙基于相同旧版本、不同材料请求重评；说明任务、候选与最终当前工作版本如何协调。
8. **重评期间新增线索**：运行中的输入不被悄悄改变；新线索可继续讨论，并显示尚未包含在本次结果中。
9. **权限收缩**：甲失去来源文档访问权或退出事项；新对话不继续借用旧会话里的受限内容，说明既有审计记录的访问政策。
10. **回流或流式中断**：Aily 已部分回答，Host 写入失败；状态准确、重复投递不重复归集、不重复触发分析。
11. **文档修订**：文件 A 从版本 1 到版本 2；历史解释仍可追溯，但不能被当成版本 2 的新结论。
12. **知识循环**：知识检索命中的是旧 AI 候选摘要；系统识别其来源并回查 Host，而不将其视为新的独立证据。
13. **一段话更新两事项**：明确选取各自相关部分、分别确定基线与权限；不能一个任务写错另一个对象。
14. **群聊协作**：如果第一阶段包含群聊，说明谁的意图触发动作、哪些成员可见、如何分享至事项；否则列为后续阶段并解释原因。

对每个场景给出用户看见什么、系统保存什么、使用哪个对象/版本、何时需要澄清、何时调用 OpenClaw、失败如何恢复。
